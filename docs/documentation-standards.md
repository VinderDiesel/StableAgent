# StableAgent 文档维护规范

> **状态：Current**。本规范定义 `docs/` 的职责边界、文档状态、命名、证据要求和变更流程。它不替代项目路线图、公共契约或阶段验收账本。

## 1. 文档类型与唯一事实源

| 类型 | 目录 | 回答的问题 | 唯一性与维护规则 |
|---|---|---|---|
| 路线图 | `docs/Roadmap.md` | 要做什么、为何按此顺序、阶段何时可进入 | 全项目仅一份；给出范围和退出条件摘要，不复制逐条测试证据 |
| 实施规格 | `docs/specs/` | 一个阶段如何实施，模块/API/工作包/测试是什么 | 每个活跃或未来阶段一份；阶段结束后保留为交接历史 |
| 验收账本 | `docs/acceptance/` | 已完成什么、如何验证、还剩什么 | 每阶段一份；完成阶段不删除，修正通过勘误附录而非重写历史输出 |
| ADR / 契约 | `docs/design-decisions/` | 为什么选择该设计，哪些不变式不可破坏 | 一项重要决策一份；Accepted 后不能静默改结论，需新增 superseding ADR 或补充 |
| 对外文章 | `docs/blog/` | 如何向外解释已交付能力与证据 | 只能引用已存在的 ADR、Acceptance 与 benchmark；草稿显式标记 Draft |
| Benchmark 证据 | `benchmarks/` + `docs/evidence/` | 指标如何获得、参数和环境是什么 | 程序在 `benchmarks/`，结果索引/解释在 `docs/evidence/`；不把未经复跑的数字写成当前结果 |
| 使用/运维指南 | `docs/guides/`、`docs/runbooks/` | 如何安装、部署、运行、恢复和排障 | P6/P7 逐步创建；命令必须可复制、前置条件明确 |
| 历史材料 | `docs/archive/` | 项目为何起步、哪些计划已被替代 | 非现行规范；文件顶部必须说明替代它的 Current 文档 |

若两个文档对同一事实出现冲突，按下列优先级处理：**可复现测试/运行输出 → 已接受 ADR 与公共契约 → 当前 Acceptance → 当前 Spec → Roadmap → README/博客 → Archive**。发现冲突时先写清勘误或 ADR，再修改实现；不能靠删除历史掩盖差异。

## 2. 目录、命名与状态标签

### 目录规则

```text
docs/
  README.md                       # 导航，不复制正文
  Roadmap.md                      # 现行阶段范围
  documentation-standards.md      # 本规范
  acceptance/                     # pN-<scope>.md
  specs/                          # pN-<scope>.md
  design-decisions/               # NN-<decision>.md
  blog/                           # NN-<topic>.md
  evidence/                       # benchmark/测量说明（按需创建）
  guides/                         # 用户/部署指南（按需创建）
  runbooks/                       # 运维演练与故障处理（按需创建）
  archive/                        # YYYY-<historical-topic>.md
```

- 文件名采用小写 ASCII、数字和连字符；现有 `Roadmap.md` 作为外部稳定入口保留大小写。
- 阶段文件以 `p<阶段号>-<简短范围>.md` 命名，例如 `p3-context-engineering.md`。
- ADR 以两位数字排序；已发布 ADR 不重编号。
- 文章以两位数字排序，标题可用中文；文件名不使用空格。
- 不在根目录新增无分类 Markdown。例外仅为 `README.md`、`Roadmap.md`、`documentation-standards.md`，以及为冻结源码路径保留的短 Redirect；Redirect 只能链接新位置，不得复制正文或成为新的事实源。

### 状态标签

每篇非 README 文档在首屏标记以下之一：

- **Current**：当前应遵循的范围、规范或操作方式。
- **Active**：当前阶段持续更新的实施或验收材料。
- **Accepted**：已接受的设计决策；后续改变要有新决策或显式补充。
- **Completed evidence**：阶段完成的历史验收记录。
- **Draft**：未完成且不可作为发布承诺的文章或设计。
- **Future**：未来阶段规格；不可被描述为已交付。
- **Archived**：保留背景和历史，不是现行实现依据。

状态只能由阶段验收结果或明确维护决定更新。不得把代码刚写完、未运行完整门禁的功能标为 Completed。

## 3. 每类文档的最低内容

### 实施规格

每份 Spec 必须包含：开始条件、完成条件、目标、范围、非目标、不可破坏契约、模块/API 设计、按顺序工作包、测试矩阵、验证命令、退出清单、下一阶段交接。涉及现有代码时必须给出文件与符号。

### 验收账本

每个可勾选事项必须包含：需求来源、可执行验证方法、对应测试或命令、结果证据、未满足时的归属。完成项引用实际文件、测试名或 CI run；不要只写“已验证”。

### ADR

每份 ADR 必须包含：背景、约束、决策、替代方案及拒绝理由、后果/代价、迁移与兼容、测试/证据、关联文档。涉及外部副作用、权限或数据时还必须说明失败和恢复语义。

### 对外文章与 README

- 内容面向读者，不重复 DoD 的逐条细节。
- 指标必须给出命令、参数、日期、环境与波动范围的链接。
- 仅声明已验收功能；Future 规划链接 Roadmap/Spec，不使用完成时态。
- 示例须能在声明的环境运行，或明确标注所需 API key、网络、Docker 或外部服务。

## 4. 文档更新流程

1. **确认事实**：先读取受影响的契约、ADR、测试、实现和现有文档；历史测试数字不是当前验证结果。
2. **选择所有者**：范围变化更新 Roadmap；实施方法更新 Spec；决定原因更新 ADR；完成证据更新 Acceptance；对外表述更新 README/文章；用户可操作流程更新 guide/runbook。
3. **成组修改**：公共 API、事件、快照、默认行为、安全边界或阶段状态变化时，必须在同一变更中检查所有入链文档、CHANGELOG、示例和代码 docstring。
4. **保留历史**：完成阶段的命令输出、CI run、benchmark 参数和竞态记录不可删除。发现误差时增加日期明确的“勘误/后续说明”，并链接现行结论。
5. **验证链接与命令**：移动文件后搜索旧路径；检查相对 Markdown 链接、README、CHANGELOG、代码 docstring 与测试说明。文档中新增命令应在对应环境实际运行，或显式标记为 Future/示例。
6. **更新索引**：新增、移动、归档、完成或废弃的文档必须同步 `docs/README.md`。不复制正文来“兼容”旧位置。

## 5. 证据与指标规范

- Benchmark 结果必须区分**历史基线**与**本次运行**，不能拿旧数字证明新实现。
- 每项对外性能结论至少同时给出效率指标和正确性/质量指标，例如 token 节省率与事实保留率。
- 崩溃恢复、外部副作用、权限、幂等和隔离结论必须带对应的集成/e2e 测试或演练记录。
- 真实 Provider、GitHub、Docker、MCP 等网络/外部依赖测试只能作为显式 opt-in 补充；离线确定性测试是 CI 基线。
- 日志、截图、请求/响应和示例不得泄露 token、API key、用户数据、仓库私有内容或不必要的完整 prompt。

## 6. 链接、语言与评审清单

- 文档内链接使用相对路径；链接文本描述目标，而不使用“这里”“文档”等泛称。
- 中文设计文档可以保留 API、文件名和术语英文；同一文档对一个概念使用一个稳定名称。
- 使用标题层级构成可读目录：`#` 仅一次，主要章节从 `##` 开始；不要为视觉效果跳级。
- 表格承载对照信息，长推理、失败模式和命令使用段落或列表。

提交前逐项检查：

- [ ] 本文档类型、状态和唯一事实源明确。
- [ ] 没有将 Future/Draft 能力表述为已完成。
- [ ] 新增或变更的事实有 ADR、测试、命令或证据链接。
- [ ] 相关 Roadmap、Spec、Acceptance、CHANGELOG、README 与代码 docstring 已检查。
- [ ] 相对链接有效，移动后旧路径没有残留引用。
- [ ] 无密钥、个人数据、内部 URL 或不必要的完整外部输入。
- [ ] `docs/README.md` 已更新，且未复制已有正文。
