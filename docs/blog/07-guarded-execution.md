# 受控执行：把 Agent 的"动手权"关进白名单、隔离与审计里

> **状态：Draft（发布前不可作为承诺）。** 本文讲的是一套**与具体项目无关的设计原理**：当 Agent 能跑命令、改仓库、发外部请求时，边界应该画在哪里，又怎样证明边界真的生效。文中代码、字段与数字均为**示意**，用来把原理讲清楚，不绑定某一套实现。演示装置全部在本地（裸 git 远端 + 工作克隆 + 假 GitHub 客户端），不读 token、不连公网；发布前需补一张「请求 → 受理 → 动作前复检 → 执行 → 审批 → 外部写」的门控顺序图，以及容器档在真实环境下的独立隔离验证。

前六篇解决的是"Agent 能不能稳定地做事"：进程死了能续跑（01）、上下文可测量（02）、副作用不丢不重（03）、能力能叠在内核之外（04）、失败有策略表（05）、长期目标能拆成可恢复的多次执行（06）。第 06 篇末尾留了一个问题：编排层回答的是"该不该起、起几次、崩了怎么接"，但**它没有回答"发出来的那条命令本身是否安全可控"**。

直觉答案是"加个判断"：拼一条 shell 字符串，正则拦一下危险字符；或者"反正是临时 worktree，隔离了就没事"；或者"模型说用户同意了，就当他同意"。这些做法在 demo 里都有效，在真实仓库里至少制造四类事故：

- **字符串不是结构**：`f"git {subcommand} {message}"` 里的分号、换行、`$()` 会被 shell 解释成控制流；正则黑名单永远漏下一种写法；
- **白名单太粗**：匹配到 `git` 就放行，于是 `git push --force` 跟着一起进来了；反过来，用前缀匹配命令名，又会把 `git-filter` 之类的同名前缀工具放进来；
- **隔离用错了地方**：worktree 隔的是"改哪份代码"，不是"能不能跑到主仓库去"——符号链接、相对路径、cwd 逃逸都能把写操作带回原目录；
- **授权没有凭据**：一段"用户已同意"的自然语言既没有策略版本，也没有资源摘要，Mandate 过期了还在生效，事后无法回答"谁批准的、批的是哪个版本"。

本篇的主张是一句能被命令证伪的口号：

> **能不能做，和怎么做，必须拆开**：执行器只认 argv 数组和已解析的路径；策略在动作发生**之前**给出结构化判定；每次判定留下可审计的一行；**隔离是变更管理，不是安全边界**。

招牌动作是**把同一个显式请求跑两遍：一遍全链路放行，一遍把五类拒绝条件分别注入，看它们各拒一次**：

```text
RUN_RESULT status=completed ticket=tk-00000001 branch=sa-00000001-... pr_calls=1 push_calls=1

REJECT_RESULT cases=5 ok=True
# 五条拒绝记录：external_calls=0，audit >= 1，effects 不新增外部动作
```

放行的口径是 `pr_calls=1 push_calls=1`（PR 与 push 各恰一次）；拒绝的口径是**外部调用恰为 0**，五类拒绝一类都不能少。把"恰好"换成"不超过"，就放走了"被拒之后还偷偷发出去一次"这种最危险的事故。第六节给出可以直接跑的命令。

---

## 一、先划边界：受控执行管的是哪一段

受控执行不是"更安全的 Agent 框架"，它只管一段很窄的路：**从"有人请求 Agent 动手"到"外部世界真的被改动"之间的那几道门**。

不属于它的先排除：模型调用的可靠性（05）、副作用的投递与幂等（03）、跨 run 的整体状态（06）、循环的契约与默认路径（04）。它们保证"该做的事真的做到"，而受控执行保证"**不该做的事连一次都发不出去**"。两者正交：outbox 管不丢不重，本篇管该不该发。

属于它的四问，缺一不可：

| 问题 | 机制 | 回答的失败模式 |
|---|---|---|
| 能不能起这个进程？ | argv 数组 + 精确白名单 | shell 注入、同名工具、参数夹带 |
| 在哪个目录起？ | worktree 隔离 + 路径收口 | 写到主仓库、符号链接逃逸 |
| 凭什么起？ | Mandate 授权 + 动作前复检 | 过期授权、发现即授权、资源漂移 |
| 事后怎么证明？ | 判定与审批落审计表 | 只有日志、没有可查询的事实 |

这里有两个最常被混为一谈的区分，先钉死：

- **发现 ≠ 授权**。外部系统里出现了一条评论、一个 issue、一次工具发现（discovery），只是"有一个请求进入了视野"；它不代表请求者被允许写这个仓库，更不代表某个工具可以被调用。受理与授权必须分成两步。
- **隔离 ≠ 安全边界**。worktree 让不同任务改不同副本、崩溃后现场还在，但它运行在同一个用户、同一套权限下。真正的安全边界需要独立的执行环境（例如容器）并**单独验证**；光是把参数拼得很严，不等于隔离已被证明。

- **换来什么**：把"Trust me"变成一个可逐格断言的判定链，外部写之前每一格都有明确答案。
- **付出什么**：多四层机制、多几张表、多一次动作前复检；每次新增动作都要同时改白名单、授权枚举和测试。
- **不这么做会怎样**：所有判断都留在调用点，最后没人能回答"这次写到底经过谁批准"——而外部世界回滚不了（03）。

## 二、命令边界：argv 数组、精确白名单、先判定后 spawn

第一道门看起来最土，却拦住了最多事故：**不要用 shell 字符串起进程**。

字符串把"程序、参数、控制流"混在一起，由 shell 决定语义；argv 数组把结构显式化，`shell=False` 之后，分号和换行只是某个参数里的普通字符，不会再变成另一条命令。示意：

```python
def deny_reason(request, *, allowlist, worktree_root) -> str | None:
    try:
        confine(worktree_root, request.cwd)          # 先 resolve，再判 is_relative_to
    except PathEscapeError:
        return "cwd_escape"                          # ① 路径先收口
    if not request.argv:
        return "empty_argv"                          # ② 空参数一律拒
    if request.argv[0] not in allowlist:
        return "command_not_allowed"                 # ③ 逐字节匹配，不猜前缀/别名
    if any(ch in SHELL_METACHARACTERS for arg in request.argv for ch in arg):
        return "shell_syntax"                        # ④ 检查所有参数，不只是 argv[0]
    return None
```

四条判定有**固定优先级**，一次只报第一条；顺序本身就是契约：路径逃逸比命令名更根本，命令名比参数里的元字符更根本。拒绝必须发生在 spawn **之前**——判定返回非 `None` 时，结果里的开始时间和结束时间相等，这是"进程根本没起来"的可断言证据，而不是靠日志里没出现输出来猜。

三个细节最容易被好心改坏：

1. **白名单只匹配 `argv[0]`，逐字节**。不做大小写归一、不做前缀匹配、不解析别名。代价是每加一个工具都要显式改表；收益是"到底允许哪些程序"有唯一答案。
2. **白名单管的是"能起哪个程序"，不是"能做哪个动作"**。`git` 在白名单里不代表 `git push` 被允许：push 属于外部写，走授权与审批那道门（第四节）；命令边界只负责把进程安全地带起来。
3. **脱敏先于截断**。输出预算默认 64 KiB，超过就截断并加尾标；但如果先截断再脱敏，token 可能正好落在保留的前半段里。因此顺序固定为"先抹掉凭据，再按总预算截断"，而且对外摘要**不包含 stdout / stderr 原文**，只给 `mode / exit / output= / duration_ms`。

- **换来什么**：拒绝是结构化结果（带稳定原因码），而不是异常；调用方必须显式处理它，测试可以逐格断言四种原因。
- **付出什么**：不认 shell 管道和 `&&`，多步操作要拆成多个 effect；精确白名单维护成本高，新工具接入慢半拍。
- **不这么做会怎样**：把同一套规则复制进容器执行器，迟早出现"本地拒、容器放"的缝。正确做法是判定函数只有一份，本地与容器档共用；这与 05「分类只有一份」是同一条纪律。

## 三、隔离：worktree 管的是"改哪份"，不是"能不能跑"

第二道门是工作目录。直觉是"给每个任务建个临时目录就行"，但临时目录必须回答四个问题：叫什么、凭什么复用、谁能清理、环境里带什么。

**命名与复用**：每个任务一个 `sa-<ticket短id>-<slug>` 目录，slug 只许 `[a-z0-9-]`，长度有上限；复用时必须**四要素全等**——远端、Ticket ID、基准引用、归属文件，任一不符就抛错并且**保留现场**，不自动删。这里最容易犯的错是"名字对就复用"：名字只是可读标签，真正决定"这是不是同一个 worktree"的是那四个结构化字段。

**路径收口**：所有传入路径先 `resolve()`，再判断是否仍在根目录内，符号链接指向外面同样拒绝。判定在策略层做一次、在真正取路径时再做一次，用的是同一个函数，所以两次结论必然同形。

**环境与凭据**：子进程不继承父进程的全部环境变量，而是拿一张固定清单（任务 ID、Assignment ID、worktree 路径、仓库、基准引用，加上 `PATH` 和 `LANG`）；git 子进程再收窄到四项（含 `GIT_TERMINAL_PROMPT=0`、`GIT_CONFIG_NOSYSTEM=1`），不让交互提示和系统配置插进来。归属文件里不写任何凭据。

**清理默认关闭**：删 worktree 要显式 `confirm=True`，默认连分支都保留。崩溃恢复后现场还在，这是 06 那套"恢复读落定事实"的前提；自动清理会把证据一起清掉。

然后是必须说清的边界：**本地受限执行器不叫沙箱**，它只是"路径收口 + 白名单 + 受限环境"，跑在和主进程同一个权限域里。容器档是可选配置，默认把网络设为 `none`、根文件系统设为只读、`/tmp` 用临时文件系统，并限制 CPU、内存、进程数、超时与输出上限；这些参数被测试锁住，说明"装配没错"，**不等于沙箱强度被独立验证过**。真要把它当安全边界，需要另外做逃逸测试与运维验证。

- **换来什么**：并发任务互不踩踏；崩溃后能回到原现场；凭据不会被子进程顺手带走。
- **付出什么**：每个任务多一次 worktree 准备与保留成本；默认不清理意味着磁盘会持续堆积，必须另有生命周期策略。
- **不这么做会怎样**：把 worktree 当沙箱用，等于把"改错文件"和"越权执行"当成同一个问题——前者靠隔离解决，后者只能靠独立验证的执行环境解决。

## 四、授权：Mandate 是带版本的能力证书，不是布尔开关

第三道门回答"凭什么"。一个能写到仓库里的授权，至少要绑定四件事：**谁**（actor）、**什么动作**（action）、**哪个资源**（resource）、**什么时候之前有效**（expiry）。把它们压成一个 `allowed: bool`，就丢掉了所有可审计性。

**默认拒绝**：受理一个外部请求时按固定顺序过门——actor 在允许列表中 → 请求明确点名了机器人 → 仓库在允许列表中 → 资源摘要落在授权范围内。任何一关不过就结构化拒绝，而且**先记一行判定、再返回**。高风险动作（push、建 PR、评论 issue / PR、请求评审）还要单独审批，审批未决时只入队一个待决记录，不产生外部调用。

**资源摘要是命题，不是路径字符串**：把资源结构化后按固定顺序序列化再取 sha256，授权绑的是这个摘要。于是"当时批准的是 src/app.py 的这次改动"是可验证的命题；文件换了一份，摘要就变，旧审批自动变旧（`approval_stale`），必须重新批准。用 `startswith` 之类的字符串前缀判路径，会把 `src/app.py.evil` 一起算进去——这是把命题降级成猜测。

**Mandate 要能演进**：旧字段语义不动，新字段一律带默认值，用 `policy_version` 区分版本；而且只有策略入口能构造新 Mandate，调用方不能自己拼一个。否则"加字段"这种兼容扩展，会变成每个调用点都要改一遍的破坏性变更——这与 04「状态模型只能加带默认值的字段」是同一条兼容性纪律。

**动作前复检**：授权不是在受理时查一次就完事。在启动、恢复、重试、准备 worktree、外部写、调用 MCP 工具之前，都要拿当前 Mandate 再判一次；版本漂移优先于过期判断（"策略变了"比"时间到了"更早需要人处理）。拒绝一旦落定就粘住，不会因为重试而变成通过。

**发现不等于可调用**：外部接入口（例如工具发现、事件订阅）只负责把请求变成结构化事实；真正 invoke 之前还要过一遍策略过滤，且过滤结果随 Mandate 变化。两个入口共用一份策略，才不会出现"发现了就能调"的暗门。

- **换来什么**：授权可过期、可撤销、可重新批准；资源漂移与策略漂移都能被同一个复检点抓住。
- **付出什么**：一次动作要过多次复检，写路径变长；审批引入人工等待，必须有对应的驻留与超时策略（06 的 `waiting` 状态正好接得住）。
- **不这么做会怎样**：把"用户说过可以"写进 prompt 当作授权，既无法验证、也无法撤销；出了事只能靠翻聊天记录。

## 五、审计：判定要落成一行的结构化事实

第四道门不拦人，但决定这套边界能不能被信任：**每次 admit / authorize / revalidate / approve 都留一行**，字段包含决策当刻的策略版本、动作、资源摘要、actor、结果与时间。

审计有三个容易踩空的点：

1. **写决策当刻的版本，不写当前版本**。策略升级后回头看旧记录，必须看到当时生效的那一版，否则审计只能证明"现在是什么"，不能证明"当时按什么判的"。这与 01「版本不明宁可报错」同源。
2. **判定与状态变更同事务**。授权结果、审批状态与入队动作要么一起落，要么一起不落；中间那道缝正是 03 反复警告的崩溃窗口。
3. **两类记录各归其位，不假装合并**：授权判定写审计表，命令边界的拒绝写成结构化结果并作为 Report 落下来。命令被拒并不自动等于"授权被拒"，把两者塞进一张表，只会让真正需要查授权的人淹在诊断噪音里。

审计还要遵守"先脱敏后落库"：资源摘要是哈希，凭据不进表，正文原文只在必要时以摘要形式出现。一行好的审计记录能回答四问——**谁、按哪个策略版本、对哪个资源摘要、做了什么判定**——而不需要翻日志。

- **换来什么**：拒绝不是黑箱；可以回答"这个外部动作当时凭什么被允许"，也可以证明"五类拒绝全都没有外发"。
- **付出什么**：多一张表、多一次事务内写；审计本身不能防止错误决策，它只让错误可被发现与追责。
- **不这么做会怎样**：事故发生后只能 grep 日志，而日志会滚动、会被截断、会在崩溃中丢——最后"有没有批准过"变成一场争论。

## 六、招牌动作：同一条请求，五类条件各拒一次

把上面四道门变成能跑的命令。在项目根目录、激活虚拟环境后执行（`--dir` 指到临时目录可避免污染工作区；示例只建本地裸仓库，不读 token、不连公网）：

```bash
python examples/05_guarded_github_task.py --phase run --dir .demo-guarded
# RUN_RESULT status=completed ticket=tk-00000001
# branch=sa-00000001-agent-fix-the-off-by-one-in-src-app-py pr_calls=1 push_calls=1

python examples/05_guarded_github_task.py --phase reject --dir .demo-guarded
# REJECT_RESULT cases=5 ok=True
# 每条拒绝：external_calls=0，audit >= 1

pytest -q --no-cov tests/integration/test_github_example.py
# 2 passed

pytest -q --no-cov tests/unit/test_command_runner.py tests/unit/test_worktree.py \
  tests/unit/test_static_policy.py tests/unit/test_repository_executor.py tests/unit/test_sandbox.py
# 114 passed
```

四组断言钉住的是"边界逐格成立"，不是"看起来跑通了"（**口径**：本地裸 git 远端 + 工作克隆 + 假 GitHub 客户端，注入时钟与 ID，无网络、无 token；macOS + 项目虚拟环境 Python 3.11.15；本次本机单次实测为 `2 passed in 0.83s`、`114 passed in 4.19s`，**耗时不是结论，断言数字才是**）：

| 场景 | 精确断言 |
|---|---|
| 全链路放行 | 请求 → worktree → 路径授权写 → 三条白名单命令 → 人工批准 → push + 建 PR；末行 `pr_calls=1 push_calls=1`；审计顺序为复检 → 授权写 → 授权建 PR |
| `actor_not_allowlisted` | 受理即拒，`audit >= 1`，`external_calls == 0`，不新建 effect |
| `mention_required` | 同上：外部请求没点名机器人，不得进入授权 |
| `command_not_allowed` | 命令边界拒绝发生在 spawn 前；`external_calls == 0` |
| `approval_pending` | 可以留下待决记录，但 `external_calls == 0`；审批前不得发外部动作 |
| `auto_merge_not_grantable` | 结构性拒绝：构造 Mandate 时就拿不到自动合并授权 |

两个细节决定这个动作能不能稳定复现：

1. **拒绝是结构化结果，不是异常**。示例对五类拒绝逐条断言原因码、审计行数、effect 数与外部调用数；如果哪条路径改成"抛个异常完事"，`REJECT_RESULT cases=5 ok=True` 立刻变红。外部调用用「**恰好**」`== 0`，不用"不超过"——后者放走的正是"拒了还发一次"。
2. **单跑测试文件要加 `--no-cov`**：仓库配置了全局覆盖率门槛，只跑定向文件会因总覆盖率不足返回非零，测试其实已经全绿。这是 05 和 06 都记过的真实复现坑。

这套动作证明的是"**判定先于动作**"：全放行时外部世界只被改动一次，五类拒绝时一次都没有。若哪天有人把 `revalidate` 挪到动作之后，或把命令拒默认变成"记个日志继续跑"，上面几条命令会立刻变红。

## 七、有没有更好 / 更省的方法

"argv 白名单 + worktree 隔离 + Mandate 授权 + 审计"不是唯一解。摊开替代方案，才知道它的适用边界：

**1. shell 字符串 + 正则黑名单**
最省，一次性脚本够用。缺点：字符串里的控制流由 shell 决定，黑名单永远漏写法；没有结构化判定，也就没有可断言的拒绝。**只有当 Agent 根本不碰外部系统时，它才是更优解**。

**2. 通用 sandbox / 容器隔离**
边界强度更高，适合运行不可信代码。缺点：它看不见 Agent 的动作语义——不知道"这条命令属于哪个 Ticket、这次 PR 批没批"；启动与镜像运维更重，且"参数很严"不等于隔离已被验证。它是安全边界的**补充**，不是授权层的替代品。

**3. 每一步都人工审批**
安全性最高，合规场景可能需要。缺点：吞吐几乎归零，审批人会疲劳到闭眼点同意。折中是把审批留给高风险动作（外部写），低风险的本地命令走白名单 + 审计。

**4. 只靠 prompt 约束 / 模型自觉**
一行系统提示就能上线。缺点：不可验收也不可撤销；模型可能把"用户说过可以"当授权，甚至编造一条审批结论。**分类必须来自结构化字段**（05），授权同理。

**5. 通用 RBAC / IAM 系统**
成熟、集中、运维熟悉，适合组织级权限。缺点：粒度通常是"角色对资源"，不覆盖 Agent 特有的步边界、资源摘要与动作前复检；与 outbox 的 effect 生命周期还要另接一层。真有统一身份体系时，它可以做底层，但上面仍要有一层 Agent 语义的判定。

**6. 默认放行 + 出事回滚**
听起来最省事，但外部世界没有回滚键：PR 已经建了、评论已经发出去了、通知已经送达。03 讲过这个道理，它在安全边界上更加致命。

**7. 每个任务一台独立机器 / 虚拟机**
隔离最强，适合真正不可信的代码执行。缺点：镜像、调度、生命周期管理成本高；而且"跑在独立机器上"依然不能回答"这条外部写批没批"——**策略层在哪种隔离档里都必须存在**。

**8. 把策略塞进 Core 的 tool selector**
看似最省，实际上把可选能力写进了公共路径，违反 04 的"默认路径保持安静"。正确位置在注入位点与 effect 执行前：默认配置不建策略引擎，启用了才多几道判定。

**结论**：当硬约束是「**动手前可判定 + 判定可审计 + 隔离只当变更管理**」时，这套组合是性价比的甜点：复杂度集中在"一次性把判定与审计定对"，而不是散落在每个调用点。没有外部写，白名单 + 路径收口就够；不需要追责，prompt 约束也能跑 demo；需要更强隔离，就把容器 / VM 加上，但别把它当授权的替身。

## 八、写在最后的检查清单

要把"动手权"真正关起来，这八条缺一条，边界就会在半年内被悄悄磨掉：

1. **argv 数组 + `shell=False`**：判定函数在 spawn 前返回稳定原因码，拒绝不抛异常；本地与容器档共用同一份规则。
2. **白名单逐字节匹配 `argv[0]`**：不猜前缀、不认别名；白名单管程序，Mandate 管动作，两者不互相代替。
3. **路径先 `resolve()` 再收口**：符号链接逃逸算逃逸；判定与取路径复用同一个函数。
4. **worktree 四要素全等才复用**，任一不符保留现场；清理需显式确认；归属文件不记凭据。
5. **子进程环境是固定清单**，git 再收窄；"先脱敏再截断"，摘要不含原文。
6. **发现 ≠ 授权，隔离 ≠ 安全边界**：外部写与工具调用各自过授权门；容器参数被锁死不等于沙箱已被验证。
7. **动作前复检**：启动、恢复、重试、准备 worktree、外部写、调用工具各有一次；资源摘要漂移让旧审批失效，版本漂移优先于过期。
8. **每次判定留一行审计**：写决策当刻的策略版本，判定与状态变更同事务；授权与诊断各归其位，外部调用断言"恰好 0"。

## 写在最后

本篇回答的是"**Agent 能跑命令、改仓库时，边界在哪里**"：命令边界把字符串变成结构、把判定挪到 spawn 之前；worktree 把并发与崩溃现场隔离开，但明说它不是沙箱；Mandate 把"谁对哪个资源做了什么"写成带版本、可过期、可复检的能力证书；审计把每次判定变成可查询的事实。于是 03 的"不丢不重"、06 的"该不该起"、本篇的"该不该发"合成一条完整链路：**先判定，再执行，执行完留下证据**。

到这里，可靠性、效率、协作、安全四条主线各自有了招牌动作，也各自积了一堆"该做 / 不该做"：状态完整边界才可存点、默认路径保持安静、状态与副作用同事务、幂等键是命题、版本不明宁可报错、不从文本猜类型、金标准护默认路径、测恢复先于测性能，再加上本篇的 argv 数组、发现 ≠ 授权、脱敏先于截断、隔离 ≠ 安全边界。它们反复出现，说明不是某一篇的局部技巧，而是可携带的设计规范——下一篇《设计规范与踩坑手册》把这些规则连同各自的反例故障收成一张清单。
