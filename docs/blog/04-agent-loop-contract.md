# Agent Loop 与事件流契约：能力只叠加，内核不修改

> **状态：Draft（发布前不可作为承诺）。** 本文讲的是一套**与具体项目无关的设计原理**：为什么新能力可以一层层加到 Agent 上，而不必改那个最核心的循环。文中代码、字段与数字均为**示意**，用来把原理讲清楚，不绑定某一套实现。发布前需补一张「状态外置 → 步边界 → 事件流 → 外层能力」的分层图。

前三篇各自解决一类问题：快照解决"进程死了怎么续跑"，上下文治理解决"这一轮发什么给模型"，outbox 解决"对外部世界做过的事不丢不重"。把它们并排看，会冒出一个更底层的问题：**这三样能力是后来一个一个加上的，凭什么每加一个都不用重写那个最核心的循环？**

这个循环（下称 loop）是 Agent 的心脏：调模型 → 解析工具调用 → 执行工具 → 把结果喂回去 → 直到完成。直觉上，加快照就得在循环里写"这里存一下"，加 token 预算就得在循环里写"这里裁一下"，加任务编排就得在循环里读外部状态。三个能力改三遍同一个文件；第四个能力来时，前面全部回归测试都得重跑，而且没人敢保证没碰坏前三个。

本文讲的就是怎么把"每加一个功能就动一次内核"，变成"**内核锁死，能力往外接**"。

> 先把三个词钉死，后文不再解释：
> - **状态外置（state externalization）**：把"跑到哪了"完整放进一个可序列化的数据对象里，循环自己不藏任何跨步的记忆。
> - **事件流（event stream）**：循环不直接返回最终结果，而是边跑边吐出"发生了什么"的事件序列，并附带每一步结束后的状态。
> - **步边界（step boundary）**：一次"模型调用 + 随之而来的工具调用"全部结束、状态达到完整一致的那一刻。它是唯一允许被切开、被保存、被恢复的时点。

招牌动作是**一行命令 + 一次哈希比对**：把默认配置下跑出来的整条事件流（含每次发给模型的消息与工具清单、终态快照、事件类型全集、契约版本）序列化成 JSON，与一份基线**逐字节**比对；再锁定内核文件的内容哈希不变。两者都过，才敢说"新能力没碰到内核的默认路径"。测试只能证明"某几条性质还成立"，逐字节比对证明的是"整条默认路径一个字节都没变"——这是两种完全不同强度的保证。

## 一、问题：能力是可选的，内核是公共的

先说清错在哪。三个直觉方案都指向同一件事——**把新能力写进循环**：

- 要能续跑 → 在循环里加 `if step % N == 0: save()`；
- 要省 token → 在循环里加 `messages = compress(messages)`；
- 要被编排 → 在循环里读任务表、判断自己该不该停。

它们各自都能跑通，但合起来会出事，原因不是"代码乱"，而是一条结构性错配：**能力是可选的，内核是所有路径的公共部分**。可选的东西会增删、会组合、会按配置开关；公共部分一旦被它改动，所有其它路径都被迫承担这次改动的风险。

更要命的是第二层后果：这些能力**都会带来自己的运行状态**（上次存到哪了、压缩摘要是什么、预算还剩多少）。如果它们寄生在循环的实例变量里，这些状态就**进不了快照**。于是进程一重启，循环能恢复消息列表，却恢复不了"压缩摘要算到哪了"——恢复出来的行为和原执行分叉，而这类分叉在测试里往往表现为"偶尔复现"。

**不这么做的代价**：每加一个能力，内核的回归面扩大一圈；能力越多，越没人敢动；最后团队的选择只剩"复制一份循环改个名字"，也就是 fork 出多个内核版本。

## 二、解法一：把状态全部外置

第一条契约：**唯一事实源是一个可序列化的状态对象**，循环不持有跨步记忆。示意：

```python
class AgentState(BaseModel):
    contract_version: str          # 语义版本，读旧快照时决定如何迁移
    run_id: str
    status: AgentStatus            # pending / running / paused / succeeded / failed
    step: int = 0                  # 已完成的步数
    messages: list[Message] = []   # 含工具结果：工具回执也是一条 message
    usage: dict[str, int] = {}     # 用量统计，只用于观察，不回灌决策
    error: str | None = None

    def snapshot(self) -> str: ...            # 序列化成一个字符串
    def loads(cls, data: str) -> "AgentState": ...  # 原样还原
```

注意工具结果没有单独字段，它就是一条 `role="tool"` 的消息——**"发生过什么"和"接下来发什么"用同一份数据表达**，不存在两份需要对齐的账本。契约还要求 `loads(s.snapshot()) == s` 无损，否则快照就是个近似值，恢复语义无从谈起。

循环这边则只借状态、不留状态：每步读传入的 `state`，用 `model_copy(update=...)` 生成**新副本**返回，不就地修改、不写实例字段。唯一例外是一个 `pause_requested` 之类的**控制信号**——它是"外部请求我停"，不是"我跑到哪了"，因此不进快照、也不参与重放等价的比对。

> 「唯一事实源」是个人话说法：**任意时刻把进程切开，能用来恢复的信息，必须全部在这一个对象里**。只要有一比特藏在循环的变量中，那一刻的快照就是不完整的，崩溃窗口也就没有了定义。

- **换来什么**：任意步边界都能安全存盘、安全重建；能力的状态只能往这个对象里放，于是它们被迫显式、可审计、可版本化。
- **付出什么**：状态模型一旦发布就**冻结语义**——只能新增带默认值的可选字段、新增枚举成员，不能改字段含义、不能删字段。所有兼容性都得在读取侧做迁移。这份约束不便宜，但它把"语义漂移"挡在了生产数据之外。

顺带澄清一个容易误传的词：这里常说"纯函数步转移"，但循环其实是 `async` 的，会 `await` 外部的模型与工具接口。**它不是数学意义上的纯函数**；准确的性质是"**状态转移无隐式副作用**"——不改入参、不写实例状态、不持跨步缓存。把这个区别讲清楚很重要，否则读者会误以为循环不能做任何 I/O，而真相是：I/O 全走注入接口，状态转移本身保持干净。

## 三、解法二：为什么产出「事件 + 事件后状态」对

循环的驱动形态大致是这样：

```python
async def advance(state) -> tuple[AgentState, list[Event]]:
    # 一步之内的所有结果，一次性写入同一个新副本
    ...

async def drive(state):
    while ...:
        state, events = await advance(state)
        for event in events:
            yield event, state        # 同一步的多个事件，共享同一份"事件后快照"
```

关键在 `yield event, state` 这一对，而不是只吐裸事件。为什么？

因为**存盘点需要一个"状态已经完整"的时刻**。一步里可能有好几个事件（调用了两个工具、产生了两条结果），如果只给事件不给状态，外层就得自己猜"存哪一条之后的状态才是一致的"；给了这一对，外层在任意事件处拿到的都是**同一步统一收敛后的快照**，步边界天然就是存盘点。

这直接解释了前三篇为什么能"叠"上来：快照能力只需订阅这个 `(event, after)` 对，在步号变化时把上一份 `after` 落盘；编排层只需读事件类型，把自己的长期记录映射过去。两者都不需要知道循环内部怎么调模型。

- **换来什么**：存盘点、暂停点、恢复点、重放挂钩点，全部收敛到同一个概念（步边界），不需要为每种能力各定义一套时机。
- **付出什么**：每步要复制一份完整状态（含全部消息）。长会话下这是实打实的内存与序列化成本，所以才要坚持"只在步边界存"，而不是每个事件都存。

**不这么做会怎样**：如果循环就地修改状态、只吐事件，那么"事件发生时状态是什么"就取决于观察者何时读取——这是一类经典的竞态。恢复时你会拿到一个"半步"的快照，重放出来的后续事件和原始执行对不上，而且没有人能说清该怪谁。

## 四、解法三：事件流契约，恰一个终止事件且居尾

事件是**冻结的**（不可变）、结构化的：`Event(type, data, step)`。类型大致八种：

| 事件 | 含义 | 是否终止 |
|---|---|---|
| `THINKING` | 模型给出本步输出 | 否 |
| `TOOL_CALL` / `TOOL_RESULT` | 工具调用与回执 | 否 |
| `CHECKPOINT` | 快照已落盘 | 否 |
| `PAUSED` | 停在步边界等人 / 等资源 | 否 |
| `RETRY` | 本步失败后重试 | 否 |
| `DONE` / `ERROR` | 运行完成 / 运行失败 | **是** |

整条流最硬的一条不变式是：**一次完整运行，恰有一个终止事件，且它位于流的末尾**。注意两个口径细节，写错的人很多：

1. `PAUSED` **不是**终止事件。单次调用可能以 `PAUSED` 结尾、一个终止事件都没有——因为这次运行没结束，只是分段了。所以"恰一个终止"是对**跨暂停/续跑合并后的完整运行**成立。
2. 恢复一个**已终止**的运行时，产出零事件、不产生新终止事件，这不是反例，而是"没有需要继续的事"。

为什么这条不变式值得如此刚性？因为**终止事件是"这次运行结束了吗"的唯一判据**。恢复逻辑靠它决定要不要续跑，编排层靠它决定要不要起下一个任务，UI 靠它决定能不能收起进度条。一旦 `CHECKPOINT` 或 `RETRY` 事件能出现在 `DONE` 之后，下游就会在"已经判定结束"之后又收到新事件：一次运行被切成两次，状态机错乱，而且错得很隐蔽。

所以终止时的快照是**静默落盘**的——写盘，但**不注入 checkpoint 事件**，就为了让终止事件保持末尾。

- **换来什么**：下游只需一条规则（"看到终止就收口"），不需要处理"结束后又来事件"的无穷分支。
- **付出什么**：任何新事件类型都必须让路，只能是非终止的、且不得插在终止之后；新增枚举成员可以，改既有事件语义不行。表达力被刻意收窄了。

## 五、解法四：能力挂在哪——两个注入位点

状态外置、步转移、事件契约都锁好之后，能力怎么接进来？答案是循环**预留极少量的位点，且默认原样透传**：

```python
assembled = assembler.assemble(state.messages)     # 位点 1：发出去的历史长什么样
specs     = selector(registry.specs(), state)      # 位点 2：这一步给模型看哪些工具
response  = await provider.acomplete(assembled, specs)
```

两个位点的调用顺序固定（`assemble` → `select`），二者都是构造时可选注入的参数，缺省实现分别是 `return list(messages)`（原样透传）和 `return list(specs)`（全量工具）。循环内部**不认识**压缩、预算、能力过滤这些词。

于是三类能力各得其所，互不打扰：

| 能力 | 挂靠点 | 是否碰内核 |
|---|---|---|
| 上下文治理（压缩 / token 预算 / 工具裁剪） | 两个位点 + 循环外层 | 否 |
| 快照与恢复（存盘 / 读最近快照续跑） | `(event, after)` 对 + 外层管线 | 否 |
| 任务编排（长期任务状态机） | 只读事件流，映射到自己的长期记录 | 否 |

还有一条容易被忽略的纪律：**默认配置下不建任何可选引擎**。三个开关全取默认值时，外层直接短路，循环走的是最朴素的那条路——不装压缩器、不跑预算、不启快照。这让"可选能力"对**不使用者**真正做到零成本、零行为变化。

真到了非要给内核开一个口子的时候（例如暂停后要把新输入喂回同一个 run），最小做法是加一个 `extra_input: str | None = None`：仅在非 `None` 时在状态**副本**上追加一条消息，默认路径与改动前逐字节一致。第三篇检查清单里那句"优先选一个默认 `None` 的可选参数"，说的就是这种口子——**先让"内核是否被动过"只有一个答案，再谈功能**。

**不这么做会怎样**：最诱人的替代是搞一套通用 hook / 回调体系（before_step、after_tool、on_finish……）。表达力确实强，但回调天然和可变状态耦合：某个 hook 悄悄改了循环里的实例变量，快照里没有它，"从快照重建 → 事件流逐条一致"这条等价断言就悄悄失效了。这不是 hook 写得好不好的问题，是它把"状态是否完整"变成了每个插件作者的自觉。

- **换来什么**：内核小到可以冻结，能力可组合、可开关、可单独测试；新增策略只需在注册表里加一项。
- **付出什么**：位点太少，表达力受限。有些需求确实塞不进这两个位点——那种情况下正确做法是**先修改契约**（并重新生成金标准），而不是找个角落硬塞进去。位点数量是刻意维持的稀缺资源。

## 六、招牌动作：怎样证明内核没被动过

讲到这里，所有保证都依赖一句话："新增能力没有改变默认路径"。这句话不能靠 code review 拍胸脯，得可证伪。做法是造一份**默认路径金标准**：

```bash
# 示意：把默认配置跑出的整条默认路径 dump 成 JSON，与基线逐字节比对
python -m demo.default_stream_dump | diff - fixtures/default_stream.json
# 无输出即相等
```

dump 的内容要覆盖到"能证明没走偏"的程度，通常包括五类：**事件流全序列、每次发给模型的 messages 与 tools、终态快照、契约版本、事件类型全集**。随机生成的 `run_id` 要归一成固定值，输出按 key 排序，否则比对会被噪声淹没。

为什么不用"跑一遍测试"就完事？因为测试断言的是**某几条性质**（终止事件恰一个、步号对得上），而金标准断言的是**整条默认路径一个字节都没变**。前者允许你无意中改了第三次调用塞给模型的工具顺序却全部绿灯；后者不会。再加一条"内核文件内容哈希锁定"，就把"没改内核"这件事也变成了机器可判的。

- **换来什么**：任何一次"我只是顺手优化了一下"都能被一行命令挡回来；跨多个能力叠加后，仍有一个不随功能增长的稳定锚点。
- **付出什么**：金标准很脆——任何**有意的**默认行为变更都会让它变红，必须走一次显式决策重新生成基线。因此它有一条配套纪律：**绝不允许靠"更新金标准"来让失败变绿**，否则这份保证会被自己人悄悄作废。

顺带说清一个常有误解：pytest 里那份"与基线相等"的断言通常是**对象相等**，真正的**逐字节**比对是上面那条 shell 命令。两者要分清，宣传时别把前者说成后者。

## 七、重放等价：为什么恢复读快照，不重放事件

第一篇讲过"恢复读一条快照、不重放事件流"，那一篇给的是结论；本篇能给出**它为什么可能**：状态外置 + 副本式转移 + 零隐式内存态，三者合起来意味着——

> 从任意一个步边界快照重建一个全新的循环实例，再往后跑，剩余事件应当与原始执行**逐条一致**。

这条性质可以参数化验证：在第 1、2、3 步各切一刀，重建三次，比对剩余事件与终态。它是"恢复语义可信"的地基——不是"看起来续上了"，而是"续上之后和没断过一模一样"。

反过来，三种常见设计会直接毁掉它：

- **hook / 回调改写隐式状态**：重建时那些状态没了，后续分叉；
- **任意时刻 `asyncio.cancel`**：产生非确定性中间态，无法定义一致的保存点（所以暂停必须收敛到步边界）；
- **chunk 级流式事件**：模型每吐一个 token 就发一个事件，重放粒度细到不可复现。

这里也解释了**为什么不选事件溯源**（只存事件、恢复靠重放）：在 Agent 场景里，重放意味着重新调用模型（不确定、且要花钱），更意味着重放工具副作用（第三篇说过，外部世界不能回滚）。快照恢复之所以合适，是因为它把"已经发生过的事"固化成数据，而不是试图再发生一次。

## 八、有没有更好的方法

"冻结小内核 + 少量位点"不是唯一解，把替代方案摊开才知道它的适用边界：

**1. 事件溯源（Event Sourcing）**
只存事件日志，状态靠重放推导，审计能力最强。
- 优点：每一次变化都有完整来龙去脉，天然可回溯；
- 缺点：Agent 的每一步都绑定一次模型调用与可能的外部副作用，"重放"既不确定也不安全。
适合审计优先、计算确定的领域；**不适合以模型调用为步的 Agent 循环**。

**2. 通用 hook / 中间件 / 插件体系**
表达力最强，生态最好接。
- 优点：几乎任何扩展点都能挂，第三方可自行扩展；
- 缺点：回调与可变状态耦合，"状态完整"变成插件作者的自觉，重放等价难以保证。
当系统**不需要崩溃恢复**、只追求可扩展性时，它反而是更省的选择——本文的严苛约束是"可恢复"带来的，不是普适美德。

**3. 模板方法 / 基类继承**
框架给一个默认循环，子类覆盖若干钩子。
- 优点：简单直观，入门成本低；
- 缺点：子类能碰到内部状态；多个可选能力一组合，子类数量爆炸；基类演进会同时冲击所有子类。

**4. 更细粒度的流式事件**
把事件切到 token / chunk 级，前端体验最好。
- 优点：实时反馈、打字机效果；
- 缺点：重放失去确定性。折中办法是**把它放在展示层**：内核仍只吐步级事件，UI 层的流式输出不进入可持久化的事件流契约。

**5. 每加一个能力就复制一份循环**
短期最快，各自独立互不干扰。
- 缺点：内核从一份变成 N 份，修复要同步 N 次，最终没人知道哪份才是对的。这是"不改内核"的字面解，也是维护噩梦的起点。

**结论**：当硬约束是「**必须可恢复 + 可选能力多 + 默认路径必须长期稳定**」时，"状态外置 + 冻结事件契约 + 极少量默认透传的注入位点 + 金标准护默认"是性价比的甜点：它把复杂度从"每次改动的影响面"转移到"一次性把契约定对"。如果去掉"可恢复"这一条，hook / 中间件更省；如果去掉"默认路径稳定"这一条，直接改内核也无可厚非。**这套设计的全部理由都来自那三条约束，缺一条就不必照抄。**

## 九、写在最后的检查清单

要让新能力"叠上来而不动内核"，这八条缺一条，契约就会在半年内被悄悄磨掉：

1. **状态只有一个事实源**，且可无损序列化；循环不藏跨步记忆。藏在实例变量里的每一比特，都是恢复时的分叉点；
2. **步转移用副本、不改入参**；别把"无隐式副作用"误传成"纯函数"——I/O 走注入接口即可；
3. **对外吐「事件 + 事件后快照」对**，让存盘点、暂停点、重放挂钩点收敛到同一个步边界；
4. **一次完整运行恰一个终止事件且居尾**；`PAUSED` 不算终止；终止态静默落盘，不追加事件；
5. **注入位点刻意保持稀少，默认原样透传**；默认配置不建可选引擎，不使用的能力零成本；
6. **给内核开口子优先用默认 `None` 的可选参数**，并用逐字节金标准替默认路径作证；
7. **禁止靠"更新金标准"让失败变绿**；有意的默认行为变更必须走显式决策重新生成基线；
8. **暂停与取消收敛到步边界**，不做任意时刻的 `asyncio.cancel`、不把 chunk 级流式事件写进持久事件流——否则重放等价无从谈起。

## 写在最后

本篇回答的是"**能力凭什么能叠上来**"：把状态外置、把步边界定死、把事件流契约冻结，再留两个默认透传的注入位点。于是快照、上下文治理、任务编排都能长在外层，内核保持到可以锁哈希的程度。

但契约锁的是"**单任务怎么稳定地跑完**"。它管不了另一类日常故障：模型这次返回 429、工具超时、某个 Provider 整体不可用。那时候该重试、该换一家、还是该停下来等人？这是下一篇《失败自愈》的主题——它同样不该改内核，但要在外层多引入一套「错误分类 → 策略」的判断，而不是往循环里塞 `try/except`。

三篇能力 + 本篇契约合起来是同一个故事的四个视角：**先把执行模型定死，再让所有可选能力在边界之外生长**。
