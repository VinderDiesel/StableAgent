# 失败自愈：把重试、换 Provider、转人工写成一张策略表

> **状态：Draft（发布前不可作为承诺）。** 本文讲的是一套**与具体项目无关的设计原理**：一次调用失败之后，怎么决定"再试一次 / 换条通道 / 停下来等人"。文中代码、字段与数字均为**示意**，用来把原理讲清楚，不绑定某一套实现。数据来自离线脚本 Provider 与注入 sleeper 的单元测试，**不是**真实模型端到端的故障数据；发布前需补一张「错误分类 → 动作 → 事件流」决策图，以及真实 Provider 的故障注入数据。

前四篇各自回答了一个问题：进程被打死怎么续跑（01）、这一轮到底发什么给模型（02）、对外部世界做过的事怎么不丢不重（03）、以及这些能力凭什么能叠在循环上而不改内核（04）。它们合起来能保证一件事：**只要这次调用正常返回，任务就能稳定地往前走一步**。

本篇要处理的是另一半现实——调用根本没正常返回。模型接口 429、网关 503、连接超时、鉴权 403、配额不足、或者一个从没见过的异常。这时候该重试、该换 Provider，还是该停下来等人？

直觉答案几乎总是同一句："包一层 `try/except`，睡一秒，再试三次。" 这行代码在 demo 里永远有效，在生产里至少制造四类事故：

- **把局部故障放大成风暴**：上游 5xx 抖动时，每个 Worker 都无界重试，流量被乘以 N，故障恢复时间反而变长；
- **重试一个根本不该重试的错误**：403 / 401 / 配额耗尽被连刷几十次，账号被锁、日志被淹、预算被烧，而真正需要做的是换钥匙或找人审批；
- **把"需要人"的任务写成"已失败"**：一旦落到终止态 `FAILED`，恢复入口就不会再续跑它，人处理完也只能重开一个 run，前面已完成的步全丢；
- **测试里真的在睡**：为了验证 3 次退避要等 3 秒墙钟，CI 变慢、时序抖动，最后只能断言"反正它成功了"，退避预算到底有没有生效没人知道。

问题的根子不是重试写得不够巧，而是**缺少一次明确的判断**：这次失败属于哪一类，这一类对应哪个动作。本文的主张是把它写成一张可验收的策略表：

> **一次失败 → 一个分类 → 一个动作**；分类函数只有一份，决策放在循环外层，状态与事件流是唯一接口，墙钟与随机是可注入的参数。

招牌动作是**把同一个"只失败一次"的任务，只换注入的异常，看事件流结尾怎么变**：

| 第一次调用注入 | 分类 | 事件流结尾 |
|---|---|---|
| `TimeoutError("gateway timeout")` | `retryable` | 恰 1 个 `RETRY`，随后 `DONE` |
| `PermissionError("需要人工授权")` | `needs_human` | `PAUSED(reason="needs_human")`，**零个终止事件** |
| `ValueError("参数不合法")` | `non_retryable` | 零个 `RETRY`，`ERROR` 收尾 |

其中重试那条还必须同时满足：`slept == [1.0]`、`error_class == "retryable"`、配了备用 Provider 时首个 `RETRY` 的 `provider_index == 1`。三条结尾互不替代——**"该重试的没重试"和"不该重试的重试了"，都是能被测出来证伪的错**。第六节给出可直接跑的命令。

## 一、先划清边界：哪一类失败归本篇管

失败自愈容易被写成一个无所不包的大兜底，那样一定越写越乱。先把不属于它的排除掉：

- **进程死亡**：由快照与恢复入口处理（01）。本篇的起点是进程还活着、只是这次调用抛错了。
- **上下文预算拒绝**：组装后的 payload 超限，同样的参数再判一次必然同样超限，属于**确定性失败**，重试纯属浪费（02）。它应该在进入循环之前收口，根本不产生一次可重试的调用失败。
- **对外副作用失败**：发通知、建 PR 这类动作有自己的重投与幂等机制（03），与"再问一次模型"不是一回事。
- **步数耗尽 / 任务永远做不完**：这是终止条件，不是瞬时故障。

剩下的才是本篇的对象：**一次本应正常的模型 / 工具调用，因为瞬时或外部条件失败了**。这类失败在事件流里长得都一样——一个 `ERROR` 事件，加上状态里一条归一化字符串 `"{类型名}: {消息}"`。

这里有个值得单独强调的纪律：**状态机只读结构化字段和这条归一化字符串，不从自然语言里"理解"错误**。错误文本是给人看的，不是给状态机读的；后面第三节会看到，文本只被允许做最低优先级的兜底判据。

顺带说清与 01 的分工，避免两篇互相重复：01 管"进程死了"，本篇管"调用挂了"；两者共用同一条保证——**重试同样不重跑已完成步**，因为重试复用的就是快照恢复那套状态语义。

## 二、分类优先级：为什么结构化证据必须压过文本

分类表只有三行，判据却必须有固定顺序：

**结构化状态码 > 异常类型名 > 消息文本特征 > 默认不可重试**

示意代码（一份函数，两个入口：异常对象、归一化字符串，最后都汇聚到它）：

```python
def classify(type_name: str, message: str) -> ErrorClass:
    lowered = f"{type_name} {message}".lower()
    code = find_status(lowered)                     # status_code: 503 / HTTP/1.1 503
    if code is not None:
        return classify_code(code)                 # 1. 结构化证据
    if type_name in HUMAN_TYPES:
        return ErrorClass.NEEDS_HUMAN               # 2. 类型名
    if type_name in RETRYABLE_TYPES:
        return ErrorClass.RETRYABLE
    if any(m in lowered for m in HUMAN_MARKERS):   # 3. 文本特征，人工类优先
        return ErrorClass.NEEDS_HUMAN
    if any(m in lowered for m in RETRYABLE_MARKERS):
        return ErrorClass.RETRYABLE
    return ErrorClass.NON_RETRYABLE                 # 4. 默认
```

三分类与动作：

| 分类 | 典型来源 | 动作 |
|---|---|---|
| `retryable` | 408 / 409 / 425 / 429、任意 5xx、连接与超时类异常 | 有界重试 + 指数退避 + Provider 轮转 |
| `needs_human` | 401 / 402 / 403 / 451、权限 / 鉴权 / 配额 / 审批类 | 强制落盘，停在 `PAUSED` 等人，不重试 |
| `non_retryable` | 其余 4xx、参数错误、未知异常 | `ERROR` 事件 + `FAILED`，终止且居尾 |

**为什么是这个顺序？** 可靠性越高的证据越先用。异常对象上的 `status_code`（或 `response.status_code`）、以及文本里形如 `status_code: 503` 的显式字段，是协议层给出的确定答案；异常类型名（按类名匹配，不引入任何 SDK 硬依赖）跨语言、跨版本相对稳定；消息文本最不可靠——"timeout" 可能出现在业务内容里，"403" 可能只是订单号的一段。所以文本只在最后兜底，而且要把正则约束到 `status_code` / `error code` / `HTTP/x.y` 这几种显式形态，**不是"在一串数字里找三位码"**。

两个细节能看出这份优先级是刻意设计的：

1. `ValueError("status_code: 429")` 会被判成 `retryable`，尽管 `ValueError` 通常意味着参数错误。理由是：既然消息里给出了协议级状态码，它比类型名更可信。代价是包装得很花哨的错误文本可能覆盖类型名判断，所以匹配形态必须收窄、必须有测试钉住。
2. 文本特征层先查人工类、再查重试类。诸如 `"forbidden 503"` 这种混合文本会判成 `needs_human`——**重试一个鉴权错误的代价，远大于停下来多等一个人**。这是"不确定时偏向保守"的具体落点。

还有一条最容易被好心改坏的规则：**未知错误默认不可重试**。直觉上"认不准就试几次"更宽容，实际上是把不确定性推给下游：一次网关抖动会被放大成 N 倍流量，而且放大的是所有 Worker 同时。快速失败留下可读的错误，让人来判断，比赌运气便宜得多。分类表因此是一张**白名单**：往里加条目是兼容性扩展（放宽行为），从里面删条目则是破坏性变更。这种不对称让演进方向天然安全。

- **换来什么**：任何一次失败的动作都可预测、可复现、可单元测试；新增一种故障只需在表里加一项，不必翻遍调用点。
- **付出什么**：分类表必须与上游 SDK 一起维护；遇到没见过的新异常，第一反应是"快速失败"而不是"自愈"，短期看会显得不够聪明。

**不这么做会怎样**：把分类散落在各个 `except` 分支里，等于每个调用点各自维护一份规则。三周之后，工具超时在 A 处重试、在 B 处直接失败，而 403 在 C 处被当成普通异常刷了十次——没有任何一处代码是"错"的，但整体行为无法推理。

## 三、有界重试：次数、退避、轮转，三件事都要有边界

分类为 `retryable` 之后，重试本身还得回答三个问题：能试几次、每次等多久、用哪条通道。

**次数边界**：`max_attempts` **含首次调用**，所以可重试次数是 `max_attempts - 1`。这条口径最常被写错，一错就把调用总数多算一次，预算与告警阈值跟着全偏。默认 3 次意味着"首调 + 2 次重试"。

**时间边界**：第 n 次重试等待

\[
delay(n) = \min(base \times factor^{\,n-1},\ max\_delay)
\]

示意默认值 `base=1.0s`、`factor=2.0`、`max_delay=30.0s`、`max_attempts=3` → 等待序列 `[1.0, 2.0]`，最大总等待 3 秒。这是一个**确定性闭式**，没有随机抖动：等待序列可以逐值断言，策略层可以脱离墙钟做纯函数验证。例如把参数换成 `max_attempts=4` 得 `[1.0, 2.0, 4.0]`；换成 `base=2 / factor=3 / cap=15 / max_attempts=8` 得 `[2.0, 6.0, 15.0, 15.0, …]`——上限真的会把序列压平。

- **换来什么**：退避预算可算、可断言、可回放；单测不必真等。
- **付出什么**：确定性退避在大规模并发下会**同步重试**（惊群）。成百上千个 Worker 同时遇 5xx，会按同一节奏一起回来。真到了那个规模，该把抖动加回来，但**加在策略层、并把随机源做成注入项**，别让"可断言"这条保证悄悄消失（第七节展开）。

**通道边界**：配了备用 Provider 时按 `retry_no % provider_count` 轮转，于是**第一次重试就落在备用通道**，而不是把主通道的预算耗尽才换。理由是经验性的：瞬时故障最常见的成因就是主通道本身（限流、区域故障、账号配额），对着同一个坏通道重试等于把预算浪费掉。轮转决策连同 `attempt`、`delay_seconds`、`error_class`、`provider_index`、`detail` 一起写进 `RETRY` 事件，事后可审计"到底换过几次、走的哪条路"。

代价不能省着不说：**换 Provider 不是换个 URL 那么轻**。不同通道的模型行为、工具 schema、计费口径都可能不同；而重试会把同一份 `messages` 在新通道上重放一次。因此轮转必须发生在**步边界**，绝不在一步进行到一半时静默换模型——后者会让"这一步到底是按哪个模型的输出走完的"变成无法回答的问题。

还有一条保证最容易被忽略：**重试不是从头再来**。修复函数只做两件事——把 `status` 洗回 `RUNNING`、把 `error` 清空；`step` 与 `messages` 原样保留。所以已完成步不会被重跑，和快照恢复是同一条保证（01）。但**当前这一步会重跑**，这就带出两个必须写进契约文档的边界：工具必须可重入；对外部世界的动作不能靠"重试次数少"来赌，要交给 outbox + 幂等键（03）。重试策略管的是"再问一次模型"，不是"再做一次转账"。

**决策放在哪儿**：只在循环外层消费 `(事件, 事件后快照)` 对时、看见 `ERROR` 事件的那一刻做判断；先发 `RETRY` 事件，再按决策等待，然后以修复后的状态重启循环。循环本身不知道"重试"这个词存在。默认策略关闭时，不启用任何自愈决策、也不改变终止方式——**可选能力对不使用者零行为变化**，这条与 04 的默认路径纪律一致。重试耗尽或 `non_retryable` 时发 `ERROR` + `FAILED`，且它仍是整条流里唯一的终止事件、位于末尾；`RETRY` 是非终止事件，不会破坏这条契约。

## 四、`PAUSED` ≠ `FAILED`：把"人"接进状态机

`needs_human` 这类失败（鉴权、权限、配额、审批）不是代码能修的。重试它们只会刷日志、锁账号、烧预算，唯一有效的动作是**把当前进度完整地交给一个人**。

做法是：状态置为 `PAUSED`、强制落盘（保留 `error` 原文供人判读）、发一个带 `reason="needs_human"` 的 `PAUSED` 事件，然后返回——**不发 `ERROR`，不产生终止事件**。

为什么不能图省事直接标 `FAILED`？因为 `FAILED` 是终止态，恢复入口读到终止态会原样返回、不再续跑。人换好钥匙、批完额度回来，任务已经"死"了，只能重开一个 run，前面所有已完成步与上下文全部作废。而 `PAUSED` 表达的是"这次运行没结束，只是分段了"：04 讲过，恰一个终止事件是对**跨暂停 / 续跑合并后的完整运行**成立，单段以 `PAUSED` 结尾、零终止事件是合法且正常的。

人处理完之后怎么接上？`resume(extra_input=...)` 把新的输入（新钥匙已生效、审批结果、补充线索）追加到**状态副本**的末尾，绝不就地改写原快照，然后从暂停点继续跑；没有可恢复的 `PAUSED` 状态时直接拒绝。这条也顺带兑现了状态外置的红利：交接不依赖那个进程还活着——重启后读回快照一样能恢复。

一个容易被当成"多余开关"的约束：**只有启用了自愈策略，才允许改变终止方式**。默认策略关闭时，403 仍然按 `ERROR` / `FAILED` 收尾。理由是语义上的：没打开可靠性层，就不该偷偷改变默认行为，否则"什么都没配"的用户会发现事件流悄悄变了。

- **换来什么**：需要人的任务不会丢进度；状态机一个新成员都不用加，复用既有暂停 / 恢复语义；`PAUSED` 快照可跨进程交接。
- **付出什么**：`PAUSED` 的运行会一直占着记录，必须有人或有系统真正来认领，否则永久滞留。因此它天然需要一个"等待人工"的外部看板与超时策略——这属于编排层的职责（下一篇 06），本篇只保证交接的接缝是干净、可恢复的。

## 五、为什么 sleep 必须是注入项

把 `await asyncio.sleep(delay)` 写死在重试路径里，看起来无可厚非，后果却很具体：验证 3 次退避要真等几秒墙钟；CI 变慢、时序抖动；"到底等没等、等得对不对"无法断言，只能退而求其次断言"最后成功了"。于是退避策略这张表实际上**没有验收**。

最小改法是把墙钟变成一个参数：

```python
Sleeper = Callable[[float], Awaitable[None]]   # 默认 asyncio.sleep

async def retry_path(..., sleep: Sleeper):
    yield retry_event(decision), repaired
    await sleep(decision.delay_seconds)         # 测试里换成记录实参的空协程
```

测试注入的 sleeper 只把实参追加进一个列表，于是可以断言 `slept == [1.0]`，或 `slept == [0.5, 1.0, 2.0]`——离线、确定性、毫秒级。更一般的原理是：**凡是墙钟与随机，都要变成可注入的参数，否则策略表就没法被验收**。这与 02 把 token 变成可测量对象、04 把注入位点保持默认透传，是同一条纪律的三次出现。

- **换来什么**："重试预算"与"实际等待序列"可以逐项对照，回归测试能抓到"退避基数被改了"这种静默变化。
- **付出什么**：构造函数多一个注入项，调用方装配稍显啰嗦。这笔代价换的是"韧性可被证伪"，很划算。

## 六、招牌动作：三种故障，三种结尾

把第一节那张表变成能跑的命令。在项目根目录、激活虚拟环境后执行：

```bash
pytest tests/unit/test_agent_recovery.py -q --no-cov \
  -k "retryable_error_retries_then_succeeds or needs_human_error_pauses_for_operator or non_retryable_error_fails_without_retrying or fallback_provider_is_used_on_retry"
# 4 passed, 14 deselected

pytest tests/unit/test_recovery.py -q --no-cov
# 32 passed
```

四个节点钉住的四组断言（**口径**：离线脚本 Provider、内存快照、注入的 sleeper 不真等；两条命令在 macOS + Python 3.11 上实测一次为 `4 passed, 14 deselected in 0.10s` 与 `32 passed in 0.07s`，耗时不是结论，断言数字才是）：

| 场景 | 精确断言 |
|---|---|
| `TimeoutError` 失败一次，之后成功 | `RETRY` **恰 1 次**、尾部 `DONE` 恰 1 个终止事件、`slept == [1.0]`、`error_class == "retryable"`、终态 `SUCCEEDED` |
| 主通道一直失败、配了备用 Provider | 首个 `RETRY.data["provider_index"] == 1`、备用 Provider 的 `calls` 非空、尾部 `DONE` |
| `PermissionError` 失败一次 | 尾部 `PAUSED`、`reason == "needs_human"`、`error` 仍含 `PermissionError`、零 `RETRY`、零终止事件；`resume()` 后 `SUCCEEDED` |
| `ValueError` 失败一次 | 零 `RETRY`、尾部 `ERROR`、终态 `FAILED` |

第二条命令覆盖分类表与退避序列本身：8 组参数化的三分类判据、5 种超时异常归为可重试、5 条归一化字符串的分类、`RuntimeError("某种没见过的故障")` 判为 `non_retryable`，以及 `[1.0, 2.0, 4.0]`、`[2.0, 6.0, 15.0, …]` 两组退避序列与 `delay_for(0)` 必须报错。

两个口径细节，写错会让招牌动作失真：

1. 断言用的是**"恰好"**，不是"不超过"。`RETRY` 恰 1 次、终止事件恰 1 个——写成"不超过"就同时放走了"该重试没重试"和"结束后又冒出事件"两类故障（03 里那条"恰好 N 次"是同一个道理）。
2. 单跑一个测试文件要加 `--no-cov`：仓库配置了全局覆盖率门槛，只跑单文件会因总覆盖率不足而返回非零，测试其实已经全绿。这是真实的复现坑，不是策略问题。

这套动作证明的是"分类 → 动作"的映射**逐格成立**：同一个任务、同一个循环，只换注入的异常，就得到三种互不相同的结尾。若哪天有人把 `needs_human` 改成了 `FAILED`，或把默认不可重试改成"认不准就试三次"，这四条命令会立刻变红。

## 七、有没有更好 / 更省的方法

"一份分类函数 + 一张策略表 + 外层决策"不是唯一解。把替代方案摊开，才知道它的适用边界：

**1. 调用点 `try/except` + 固定 sleep**
最省，一次性脚本完全够用。缺点：策略散落在每个调用点，无界重试、分类与状态机脱节，无法表达 `PAUSED`，也无法验收"等了多久"。**只有当没有崩溃恢复需求、没有人工交接时，它才是更优解**。

**2. 通用重试装饰器 / 重试库**
工程上最省事，退避、抖动、超时一应俱全，跨语言都有现成实现。缺点：它把"重试"当成**函数级属性**，看不见 Agent 的步边界与已完成步，也没法把 `needs_human` 落成持久状态；重试计数在进程内存里，崩一次就归零。当系统不需要崩溃恢复、不需要把失败交给状态机时，它反而比本文这套更划算——正如 04 所说，那些严苛约束是"可恢复"带来的，不是普适美德。

**3. 队列 + 死信重投**
把失败任务重新入队、由独立的消费者重投，天然可审计、可跨进程。适合**对外副作用**与长事务（03 的 outbox 就是这条思路）。缺点：对"同一步里换条通道再问一次模型"太重，延迟、运维面都上去了，而且它不知道 `messages` 走到哪一步。

**4. 熔断器 / 健康探测后主动切换**
多 Provider、大规模流量下更优：能记住"这条通道刚坏过"，避免把预算浪费在已知坏通道上。缺点：健康度本身必须作为**可序列化的状态外置**，还要处理误判、半开状态、探测流量。本文的确定性轮转是它的极简版：不记忆、不探测，代价是"不知道备胎是不是也坏了"，第二次重试可能又轮回主通道。

**5. 把错误塞回 prompt，让模型自己决定**
看似最智能，实则不可验收：模型可能把 401 当成普通上下文继续消耗预算，也可能编造一个"已重试"的结论。分类必须来自结构化字段，不从自然语言猜类型——这条在第一节就已经划下。

**6. 加入随机抖动（jitter）**
抗惊群确实更好，是大规模并发下的正确方向。代价是等待序列不再能逐值断言。折中办法是把抖动做成策略层的一个**注入随机源**：测试注入固定序列，仍是确定性的；生产注入真随机。别为了抗惊群把"可验收"整条丢掉。

**7. 无限重试直到成功**
看起来最稳妥，实际是把上游故障放大成自身故障，且永远无法区分"瞬时抖动"与"这件事根本做不成"。默认不可重试这条规则的全部意义，就是挡住它。

**结论**：当硬约束是「**必须可恢复 + 默认路径必须稳定 + 失败要能落到状态机**」时，"一份分类函数 + 一张策略表 + 外层决策 + 注入墙钟"是性价比的甜点，它把复杂度从"每个调用点的临场发挥"转移到"一次性把分类与动作定对"。去掉"可恢复"，装饰器重试库更省；去掉"状态机语义"，固定 sleep 也够；规模大到需要抗惊群，就该把抖动和熔断器补上，但不要因此放弃"分类只有一份、动作可证伪"这两条底线。

## 八、写在最后的检查清单

要把"韧性"从运气改成策略表，这八条缺一条，半年内就会被悄悄磨掉：

1. **分类判据有固定优先级**：结构化状态码 > 异常类型名 > 消息文本特征 > 默认；一份函数、两个入口，别让两套规则漂移。
2. **未知错误默认不可重试**，分类表是白名单；放宽是兼容扩展，收紧是破坏性变更。
3. **`max_attempts` 含首次调用**；退避有上限、总预算可算；确定性序列可断言，需要抗惊群时把抖动做成注入项。
4. **配了备用 Provider 就第一次重试轮转**，且只在步边界换通道，不在步内静默换模型。
5. **重试只剥失败标记**，`step` / `messages` 原样保留；当前步会重跑，所以工具可重入、对外动作交给 outbox + 幂等键。
6. **`needs_human` 停在 `PAUSED` 并强制落盘**，保留 `error` 原文，绝不发终止事件；`resume()` 把新输入追加在状态副本上。
7. **自愈决策只在外层看见 `ERROR` 事件时发生**；默认策略关闭时不建存储、不改终止方式，默认事件流保持安静。
8. **墙钟与随机必须可注入**；断言"恰好"而非"不超过"，把重试预算与实际等待序列逐项对照。

## 写在最后

本篇回答的是"**这次调用失败了，接下来该做什么**"：先把失败归到三分类之一，再由策略表决定有界重试 / 换通道 / 停下来等人；决策全部发生在循环外层，靠状态与事件流接口，不往内核里塞 `try/except`。于是 01 管进程死亡、本篇管调用失败，两者共用"不重跑已完成步"的保证，而 04 的契约让这一切不必改内核。

但这里能自愈的仍是**一个 run 内部**的失败。一个长期目标往往要拆成许多次 Worker 执行，跨 run 的整体进度、依赖与槽位由谁记录，崩溃后整体怎么恢复？这是下一篇《Ticket 编排》的主题。
