# Agent Checkpoint 机制的深度设计与实现

> 状态：初稿（P2 配套产出 G1）。素材取自 ADR-02 `docs/design-decisions/02-checkpoint.md`
> 与 P2 实测：崩溃恢复用例 `tests/integration/test_crash_recovery.py`、
> 开销基线 `benchmarks/recovery_time_benchmark.py`（本机 12 步 / 3 轮，SQLite 后端）。
> 发布前需要补：一张流程图、真实模型（非脚本 Provider）的端到端数据。

Agent 框架的 demo 都在演示"能跑通"，生产环境要的是"跑挂了还能接着跑"。这两句话之间
隔着十几个设计决策。这篇讲清楚 StableAgent 的 checkpoint 是怎么做的，以及每个决策换来
了什么、代价是什么。

招牌动作只有一个：**运行中 `SIGKILL` 掉进程，重启，从最近快照续跑到完成。**
这个动作在 CI 里是自动化用例——subprocess 起进程，看到 `step=2` 的 checkpoint 事件就把
它打死，再起第二个进程读回快照跑完，末行输出：

```
RESUME_RESULT status=succeeded steps=4 provider_calls=2
```

`provider_calls=2` 是全部重点所在：任务共 4 步，崩溃时第 1、2 步已完成并落盘，恢复后只调用了
2 次模型（第 3、4 步）——已完成的步一次都没有重跑。

顺带一个只有真跑过才会遇到的坑：**回看式落盘把击杀点挤到了终止事件旁边**。最初的演示是
3 步、击杀第 2 步快照，本地预跑 CI 矩阵时（Python 3.10）偶发"kill 没杀死"——因为第 2 步的
快照是和第 3 步（终态）的第一个事件同时打印的，父进程读到这行时子进程只剩几毫秒寿命，
信号发出去时进程已经自己退了。实测可击杀窗口（读到快照 → 子进程自然退出的时长，12 轮中位）：
3 步设计 13 ms，改成 4 步（击杀点之后仍剩一整轮 provider 往返）65 ms；把单次往返拉到
200 ms，旧设计还是 16 ms，新设计 220 ms——**窗口从"和调度竞速"变成"随往返时长线性放大"**。
保存点的语义决定了外部观测到的时序，这条已经写进 ADR-02 的后果节。

## 一、保存点选在哪：步边界，不是任意时刻

第一直觉是"每秒存一次"或者"每个 token 存一次"。都不行——任意时刻切开的那个状态是没
定义的：工具调用发出去了、结果还没回来；或者 assistant 消息写了一半。恢复时你无法判断
该重放还是该继续。

StableAgent 的保存点 = **步边界**。一步是 `thinking → tool_call → tool_result` 这个不可
分割的最小完成单元。于是"快照里 step=k"这个命题有确定含义：**第 k 步已经完整结束**。
恢复时从 k+1 开始，不需要任何判断。

这个决定直接来自执行引擎的契约（ADR-01）：`pause()` 本来就在步边界生效。暂停点和保存点
同构，不是巧合——它们要解决的是同一个问题："什么时候的状态是完整的"。

代价立刻出现：**工具调用必须可重入**。崩溃窗口是"当前正在跑的那一步"，最坏一步，恢复时
这一步会重跑。检索类工具无所谓，"转账"类工具不行。框架只能把这条写进文档，强制不了。

## 二、什么时候写：回看，而不是前看

保存点定了"哪里可以写"，还没定"什么时候写"。

**前看式**（第 k 步结束就写）看着最自然，但它有个隐蔽的错误：第 k 步的 `tool_result` 事件
已经发出去了，`state.step` 也要自增了，如果进程恰好在这中间被杀，磁盘上的快照和内存里
的"已发到哪"就不一致——恢复后会把第 k 步重跑一遍，而消费方早就看过第 k 步的结果了。

**回看式**：第 k 步的快照，在**第 k+1 步的第一个事件到达时**才落盘。因为那一刻才真正证明
第 k 步彻底结束了——模型都开始第 k+1 步了。实现上这是个极简的滑动：

```python
async for event, after in engine.drive(current):
    if pending is not None and after.step != step_seen:   # 新步的第一个事件
        record = await self._save(pending, force=False)   # 补发上一步的快照
        if record is not None:
            yield self._checkpoint_event(record), pending
    step_seen, pending = after.step, after
    yield event, after                                     # 事件本身即时透传
```

两个细节各值一次返工：

1. **事件即时透传**。不能把事件攒到下一步再发——那样 `pause()` 的响应会延迟一整步，
   执行契约就废了。所以是"事件走前面，快照补后面"。副作用是 `checkpoint` 事件的 `step`
   可能小于当前流位置，消费方不能假设它单调跟随。
2. **终止态静默落盘**。`done` 的那份快照**必须**写盘（否则重启后会把已成功的 run 当未完成
   再跑一遍），但**不能**发 `checkpoint` 事件——契约要求 `done|error` 恰好一个且位于流的
   末尾。多一个事件就破坏一条不变式。取舍：可见性让位于一致性，改用 `agent.last_checkpoint`
   属性供调试取用。

## 三、崩溃窗口有多大：用数据说话

窗口大小 = `auto_save_every`。=1 时每步落盘（窗口 0 步，写最多），=0 时只在暂停/终止点
落盘（窗口最大，但暂停点绝不丢）。开销是多少？跑基线（12 步脚本任务，SQLite，3 轮中位数）：

| `auto_save_every` | 端到端耗时 | 落盘次数 | 相对 =0 的倍率 |
|---|---|---|---|
| 0 | 1.5 ms | 1 | 1.0× |
| 1 | 6.6 ms | 12 | 4.4× |
| 2 | 3.9 ms | 6 | 2.6× |
| 5 | 2.3 ms | 3 | 1.5× |

每步都存，12 步多花 5 毫秒。拆开看更有意思：

- 单次快照写入：**平均 0.56 ms，p95 0.77 ms**
- 纯序列化（`AgentState` → JSON）：**0.003 ms**

**序列化不是成本，落盘才是**（差两个数量级）。这条决定了框架该在哪一侧做优化：把快照
压缩、把 payload 变小基本没用；要么降低写频率，要么把 fsync 挪出关键路径（批处理、
WAL、异步刷盘）。反过来，一次写入 0.5ms 也意味着"每步都存"在生产里是可负担的默认——
真实任务里一步的耗时是大模型一次往返（秒级），快照开销被淹没在噪声里。

恢复侧同理：读最近一条快照 + 版本迁移 + 反序列化 = **约 0.05–0.12 ms**，量级由"库里还留着几条
快照"决定（历史裁剪要扫这几行），与"被恢复的那条有多大"基本无关——40 条 8 KB 裁到 3 条实测
0.046 ms，和 5 条 1.1 KB 的 0.053 ms 同档。这是"存状态快照"相对"存事件流（事件溯源）"的决定性
优势：后者要把历史事件全部重放一遍才能重建状态，恢复时间随任务长度线性增长，而 Agent 的历史
长度是单调增长的。

## 四、并发与幂等：只做该做的，不做想象的

- 同一 `run_id` 的写入串行化（`asyncio.Lock` per run）：回看落盘和强制落盘（暂停、终止、
  转人工）会交错，不锁就会出现"新快照先落盘、旧快照后落盘"。
- 主键 `(run_id, step)` 覆盖写 → 同一步重复保存不产生第二条记录。SQLite 用
  `INSERT OR REPLACE`，Redis 用单 key 的读-改-写，内存后端用 dict key。
- **不提供跨进程锁**。同一个 run 只应该有一个驱动者，多进程同时驱动属于误用；引入分布式
  锁防误用的代价（多一个外部协调面）大于收益。

## 五、后端取舍：三套实现，一组断言

存储协议面刻意小——`save / load / records / delete` 四个异步方法，后端差异不许泄漏到上层。

| 后端 | 为什么存在 | 代价 |
|---|---|---|
| memory | 单测基线；顺便证明"进程重启即丢失"这条反面事实 | 无持久性 |
| sqlite | 单文件、零服务、主键天然幂等，**默认交付路径** | 单机 |
| redis | 一个 run 一个 key、值为记录数组 JSON，跨进程可见 | 读-改-写牺牲同 key 并发写最优性 |

两条硬约束：
- **同步驱动必须下沉**。`sqlite3` 是同步库，直接 await 不了；实现走
  `asyncio.to_thread` + 实例内 `asyncio.Lock`，调用面保持纯异步。
- **redis 是注入项，不是依赖**。框架只要求客户端满足 `get/set/delete` 三个协程
  （`redis.asyncio` 直接兼容）。未安装 redis 也能 import 本包并跑完全部测试——CI 用
  fake client 验，真实 Redis 用例由环境变量开关，不可用时 **skip 而不是 fail**。

三套后端共享同一组一致性断言（无损往返、按 run 隔离、按 step 升序、取最新、同步覆盖写、
历史裁剪、删除）：新加第四种后端时，这组参数化用例就是它的验收标准。

## 六、版本迁移：宁可不猜

生产数据不能靠猜。规则只有三条：

- 缺 `contract_version` 字段 → 按**最早已知版本**处理（那是框架的首个版本，语义确定）；
- 已知旧版本 → 沿 `MIGRATIONS` 链逐级升级（`1.0.0 → 1.1.0` 只做一件事：补齐新增可选字段
  的默认值，因此与 Pydantic 的默认值语义等价，可以双向验证）；
- **高于当前版本、未知版本、版本串解析不了 → 抛 `SnapshotVersionError`**，运维者升级框架，
  而不是让代码把语义漂移写进生产数据。

迁移发生在 **checkpoint 读取侧**（`migrate_state`），`AgentState.loads` 保持严格、签名不变。
这样旧快照能读，但没有任何一条路径可以"悄悄"接受语义不明的数据。

## 七、失败自愈：分类决定动作，不决定运气

checkpoint 管"进程死了怎么办"，另一半问题是"这次调用失败了怎么办"。判据优先级固定：

**HTTP 状态码 > 异常类型名 > 消息文本特征 > 默认**

默认 = **不可重试**。这条值得单独说：直觉上"认不准就试几次"更宽容，实际是把不确定性
推给下游——一次网关 5xx 风暴会放大成 N 倍流量。宁可快速失败，让人来看；分类表随时可以
按新增条目放宽，那是兼容性扩展。

三分类对应的动作：

- `retryable`（超时/连接/429/5xx）：指数退避 `min(base × factor^(n-1), max_delay)`，
  重试次数 `max_attempts - 1`（`max_attempts` 含首次调用）。重试的"续跑"是把失败标记剥掉
  （`error=None`、状态回 RUNNING），`step` 与 `messages` 原样保留——**所以重试同样不重跑
  已完成步**，与 checkpoint 共用同一条保证。
- 配了 fallback Provider 时，按 `retry_no % provider_count` 轮转，于是**第一次重试就切到
  备用 Provider**（瞬时故障最常见的成因是主通道本身），而不是把主通道的重试次数耗尽才换。
- `needs_human`（401/403/配额/审批类）：**停在 `PAUSED`，不是 `FAILED`**。这类错误不是
  代码能修的；人处理完调 `resume()` 就续跑——复用暂停/恢复的既有语义，状态机一个新成员
  都不加。
- `non_retryable`：直接 `error` 收尾，且它仍然是流的最后一个事件（F4）。

`sleep` 是注入项，不是写死的 `asyncio.sleep`。这条看起来是测试洁癖，实际换来的是
**"重试实际等待序列与预算次数完全一致"可以在毫秒级断言**——不真等。

## 八、写在最后的检查清单

要给自己的 Agent 加 checkpoint，这七条缺一条都会在生产里出事：

1. 保存点必须是"状态完整"的边界，不能是时间片；
2. 写盘时机要在"这一步确实结束了"之后（回看），不是事件发完就走（前看）；
3. 终止态也要落盘，但可以不发事件——别让可见性破坏流结构；
4. 崩溃窗口 = 一步，所以工具必须可重入，这条要写进契约文档；
5. 版本不明宁可报错，不要猜；旧快照能读比新快照能写更要紧；
6. 存储层的同步依赖要下沉到线程，第三方客户端要作为注入项而非硬依赖；
7. 先测恢复，再测性能：恢复是"重放全部历史"还是"读一条快照"，属架构级分叉，不是调参问题——
   前者耗时随任务长度线性增长，后者只随"库里保留几条快照"缓慢上升（实测 0.05–0.12 ms）。
