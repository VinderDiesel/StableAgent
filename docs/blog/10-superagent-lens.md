# 用 Super-agent 的五面镜子，看 StableAgent 的设计选择

> **状态：Draft（发布前不可作为承诺）。** 本文是一篇**外部视角解读**：用 DeepSeek Harness 团队公开的 Super-agent 架构探索当透镜，检查 StableAgent 的设计选择回答了哪些问题、又留了哪些空白。文中概念来自公开文章与研究原型（**不是 DeepSeek 正式产品**，实验负载是合成的）；StableAgent 部分基于已交付能力与可复现证据，代码与数字均带口径。发布前需补一张「五模块 → 运行时能力」的对照图，以及真实外部接入口的观察数据。

2026 年 10 月 31 日，DeepSeek Harness 团队发表《Super-agent 设计探索：迈向更自主的 Agent 系统》，并放出研究原型 `dsh-superagent-prototype`。它提出一个很实在的判断：**单任务的上限取决于模型能力，多任务的上限取决于人的注意力**——一个人通常只能同时跟进 3 到 5 个活跃会话。任务一多，人就在对话之间做会话管理、同步上下文、转发报错、判断哪个需要介入；AI 干了执行，人却成了调度瓶颈。

文章把这个目标写成四个体验词：**连续、高效、主动、持久**，并用五个模块支撑它——Router / Worker 双层架构、事件驱动、异步交互、计算与状态分离、外部 Watchdog。这不是产品发布，而是一份架构笔记：公开原型与内部版本并不完全一致，部分设计尚未实现，实验是合成负载；原文自己也把 Router 拆分、跨月记忆、多实例协作、人随时介入、提示词注入与凭据安全列为开放问题。

正因为它是**设计探索**而不是功能清单，适合拿来当镜子：不问"StableAgent 有没有抄这五个模块"，而问"**同一个问题，StableAgent 把答案放在了哪里，代价是什么**"。前面的 01–07 篇讲单篇能力，本文退一步看整体形状。

招牌动作是一次**常驻 Router 的离线演练**：让事件进来、决策留痕、人工审批、崩溃恢复、对外只发该发的消息：

```text
BETA_RESULT tickets=3 resumed=1 external_comments=1 duplicate_tickets=0 bot_triggers=0
BETA_REPORT {"approvals": {"comment_issue:approved": 1, ...}, "decisions": {"accept": 4, "observe": 3},
             "effects": {"github_comment:succeeded": 1, ...}, "recovered_assignments": 1,
             "triggers": {"ci_status": 1, "issue": 3, ...}, "would_accept": 1}
```

`duplicate_tickets=0`、`bot_triggers=0`、`external_comments=1` 三个数字合起来才是重点：事件重复与机器人自言自语变成 0，人工只被真正需要决策的那一次打断，推断出来的候选任务只记录不执行。第八节给出可跑命令与口径。

---

## 一、第一面镜子：双层架构——把协调与执行分开

Super-agent 的双层很清晰：**Router 常驻，统一承接入口、跨任务决策、分派与汇总；Worker 在隔离上下文里干活，把关键状态回报给 Router**。原文甚至说 Router 可以不配 Bash 工具——它管的是"该谁做、做到哪了"，不是"怎么写这行代码"。

StableAgent 把这条边界写成包与方向：**协调侧**由 Router 服务承接 Trigger、Thread、Decision、Subscription 与 Ticket 的创建；**执行侧**是调度器加 Worker 执行器，按 Ticket 起 Assignment、在独立 worktree 里跑（06/07）。依赖方向是单向的，底层内核不知道上层协调者的存在；这与第 04 篇"内核锁死、能力往外接"是同一条纪律。

两个对齐点值得单独说：

- **入口只产事实，不建任务**。外部接入口（Source）的职责是把 GitHub 事件标准化成 Trigger 并维护读取游标；它不能创建 Ticket、不能调 Worker、不能扩大授权。回写通道（Channel）只描述"往哪发"，不携带 actor、scope 或 action——**能发消息不等于有权动手**。这正是第 07 篇"发现 ≠ 授权"在协调层的复刻。
- **Router 也只是"唯一写入口"，不是"唯一执行者"**。真正的状态机仍在领域服务里：显式、授权过的请求才建 Ticket；活跃 Ticket 的后续讨论作为输入扇出；推断型候选落一条 Decision 而不是直接起活。

- **换来什么**：一个入口管调度、一类 Worker 管交付；人被从"多个窗口之间切来切去"里挪开。
- **付出什么**：多一层路由、多一套记录，跨层调用必须走结构化接口；协调层出错时，所有任务都会等它。
- **不这么做会怎样**：所有事件进同一个会话，任务细节互相污染；每条事件新建会话，任务之间的关联又断了——原文对这两端的描述，恰好是第 06 篇"单 Worker 可靠 ≠ 多任务协作可靠"的另一种讲法。

## 二、第二面镜子：事件驱动——先确定性过滤，再让模型判断

Super-agent 把群聊、邮件、评论、CI 结果这类半结构化变化叫 **Trigger**，并强调两级过滤：**程序先按来源、白名单、群组范围这些确定性条件筛一遍，语义判断才交给模型**（原文称为 Fast Path / Slow Path）。它还有 Thread 订阅直通：同一话题的后续事件程序直接送给订阅者，不必每次由 Router 转发。

StableAgent 在这一层做得更"账本化"：

| 环节 | 做法 | 对应原文问题 |
|---|---|---|
| 事件不可变 | Trigger 冻结、字段封死；payload 取规范化 JSON 的 sha256 作封印 | "哪些值得看"之前，先保证事件本身不被改写 |
| 去重 | 外部 ID 唯一键 + 库层插入忽略；游标与事件同事务推进 | 重复事件不能造成重复任务 |
| 一级过滤 | 入口过滤自身机器人事件；actor / 仓库 / 动作按白名单判定 | Fast Path 用代码解决 |
| 二级判断 | 显式请求走策略准入；推断候选走确定性评估器，默认只记 `observe` | Slow Path 也不等于"直接执行" |
| Thread 直通 | `own` / `context` 两种订阅，后续事件定向扇出给活跃 Ticket | Worker 订阅 Thread，评论直接进上下文 |

这里最值得强调的是**扇出不扩大授权**：`context` 订阅能把 PR 评论、CI 结果送进活跃任务，但它既不能放大 Mandate，也不能凭自己创建执行任务。DeepSeek 原文提醒"共享事件让 Worker 有机会发现彼此的操作，但不保证冲突自动消失"，StableAgent 的答案是把授权与资源摘要绑定、动作前复检（07）——**上下文能共享，权限不能搭便车**。

Inline / Spill（把近用信息放窗内、长内容留窗外按需召回）在 StableAgent 里不是"记忆系统"，而是第 02 篇那套可测量上下文治理：压缩保留完整的工具调用对、已用工具常驻、预算动作可观测。原文把跨月记忆列为开放问题；这里也不假装解决——**长上下文治理 ≠ 长期记忆**。

- **换来什么**：事件把系统推着往前走，不用人逐条转发；重复与自触发在进模型之前就被挡掉。
- **付出什么**：确定性规则要持续维护；事件越标准，语义空间越窄，某些"看起来相关"的事会被程序先筛掉。
- **不这么做会怎样**：每条事件都问一次模型，成本随噪声线性上涨；而"机器人自己发的评论"被当成新请求，就会形成自激循环。

## 三、第三面镜子：异步交互——长时间工作不占住对话

原文描述的异步 ReAct 是：`start()` 启动后台任务就先返回，结果完成后作为新事件送回；必要时 `stop()`；用户临时改主意，新输入在**当前推理步结束后**被处理，而不是等整条命令跑完。它特别说明"全双工"不等于模型能在任意推理瞬间无延迟响应。

StableAgent 把这件事落在步边界上，而不是塞进模型循环：暂停收敛到步边界（01），`needs_human` 落 `WAITING` 并释放并发槽位（05/06），外部新输入在驻留边界由受控投递 effect 追加（06），运行面另有可持久化的暂停/恢复控制与单实例锁——锁随库走、进程崩了按过期时间失效，不依赖操作系统文件锁。对外通知也被刻意克制：确认一次、需要决策时结构化提问一次、结果一次、失败一次；常规进度与 CI 更新默认只进监管入口，不刷屏。

- **换来什么**：长任务在后台推进，前台还能沟通；人只在"需要决策"和"结果可用"时被叫到。
- **付出什么**：消息顺序、驻留状态与恢复接缝都要显式管理；"随时介入"其实是"在完整状态边界介入"，这是有意收窄的承诺。
- **不这么做会怎样**：同步调用占住会话，用户的新要求排在一小时后的命令之后；或者反过来，任意时刻抢占推理，把状态切在半步——第 04 篇讲过，那种状态没有定义。

## 四、第四面镜子：计算与状态分离——让进程可替换，不让工作丢

原文的"存算分离"分两层：计算放进可重启、可替换的无状态容器，会话等长期状态放数据库；Agent Loop 与执行环境再分离，环境相关的活交给端侧 daemon（BYOM）。它明确提醒：**"无状态"说的是计算容器的组织方式，整个系统仍然要保存状态**；云端在跑也不代表关机的本地设备随时可用。

StableAgent 是这个原则在小尺度上的实现：

- **一个事实源**：`AgentState` 可无损序列化，循环不藏跨步记忆；步边界快照落到存储，恢复读快照、不重放事件（01/04）。
- **一层同事务账本**：Trigger、Decision、Subscription 与 Ticket、Assignment、Effect 可以在同一个事务内落库；游标不得先于事件推进，任一步失败整体回滚（03/06）。
- **所有权可恢复**：运行时锁、失败 effect 回收、Assignment `interrupted → relaunch` 都从存储推导，不信任内存里"谁在跑"的印象（06）。

- **换来什么**：进程被杀、容器被换、机器重启，工作都从落定的事实继续；不需要让人重新同步上下文。
- **付出什么**：每个状态转移多一次写库与序列化成本；"状态完整"变成硬契约，随手在内存里加个字段就会破坏恢复语义。
- **不这么做会怎样**：设备休眠工作就停；恢复时靠重放事件重建状态，而 Agent 的事件绑定模型调用与外部副作用——既不确定的花钱，又可能把外部动作做第二遍（01/03）。

## 五、第五面镜子：外部 Watchdog——盯的不只是"进程还活着"

原文的 Watchdog 是主系统之外的独立会话，由定时消息驱动：既查接口报错、状态恢复失败这类基础设施问题，也用模型判断 Worker 是不是在原地打转；它自己有工具，维护者能问"为什么卡住"。结论也很诚实：Watchdog 本身也会判断错，**不能承诺长期运行绝不失败**。

StableAgent 没有同名组件，但把"看住任务在前进"拆进各层的接缝里：

- 调用失败按分类走有界重试、退避与轮转；鉴权类落 `WAITING` 等人，不刷重试（05）；
- 任务级 deadline 到期取消 Assignment、把 Ticket 置为 `blocked`，并写一条带结构化原因的报告（06）；
- 外部写走审批门与审计，默认拒绝、动作前复检；命令边界的拒绝是结构化结果而非日志（07）；
- 监管视图只读、按**可行动性**排序：待审批 → 失败 effect → 等待人工的 Ticket → 可验收的 Ticket；源健康与队列负载单独成栏。视图不返回原始载荷，只给结构化摘要；
- 自治档默认 `observe`，推断候选只记 `would_accept`；`auto` 有代码与离线演示，但默认规则关闭、默认拒绝，运行时装配并不自动注入准入门——**能开、能关、可审计、可回滚，不等于默认开**（详见第八节）。

- **换来什么**：看门功能落在各自最懂的地方——调用层懂失败类型，编排层懂 deadline，控制层懂授权，视图层懂人的注意力；不需要一个"万能监控 Agent"。
- **付出什么**：没有单点可以问"现在到底谁在看门"，诊断要跨几份记录；监管视图只给摘要，想深挖还得回到事件与报告。
- **不这么做会怎样**：只做进程存活探测，"进程活着但任务原地转"就永远发现不了；只靠模型自觉判断进展，又回到不可验收。

## 六、镜子照出的空白：不能照抄的部分

这面镜子也照出 StableAgent 还没有的东西，写清楚比含糊带过更有用：

| 原文讨论的方向 | StableAgent 现状 | 为什么不能假装解决 |
|---|---|---|
| LLM 驱动的动态评估器 | 当前只有确定性规则评估器；评估接口是窄协议 | 语义候选的判断可解释、可复现，才配进审计链 |
| 投机执行（后台静默复现再交付） | 有"先记录候选、不执行"的 `observe`，没有静默动手 | 在授权边界上，"先做再说"必须先解决凭据与提示词注入 |
| 云端 + 端侧 daemon / BYOM | 执行与状态解耦，环境隔离靠 worktree 与可选容器档 | 隔离不等于安全边界；容器参数被锁死也要独立验证（07） |
| 跨月记忆、多实例上下文隔离 | 上下文治理与快照解决单任务长跑，不解决跨月记忆 | 把"长上下文"当"长期记忆"卖，是概念偷换 |
| 规模实验数据 | 只有固定规模下的离线基准，且明确不外推 | 对方的 p50 / p95 来自合成负载，不能当本项目的性能承诺 |

DeepSeek 的实验值得引用，但必须连口径一起引用：约 300 条消息、其中约 20 条工作请求、每种方案重复 5 次，编码工作用"只消耗时间"的工具代替；在该负载下 Super-agent 的任务完成时间 p50 为 12.4 分钟、p95 为 15.7 分钟，而中性提示下单会话 + 子代理方案的 p95 为 29.5 分钟。去掉直通机制后，Router 决策次数增加约 30%，读缓存 token 从 2323 万升到 3177 万（约 37%）。这组数字支持的是"**在该合成负载下，直通减少了路由开销**"，不是"任何任务都能省 37%"，更不是稳定运行的 SLA。

## 七、如果只要一个 demo：更省的路在哪里

五面镜子很容易让人觉得"全都要"。把替代方案摊开，才知道每一层的适用边界：

- **单会话 + 工具调用**：一个任务、一个窗口，最省也最快；只有当工作确实能在一次运行里做完时，它才是更优解。
- **更强的模型**：直接提升单任务上限。但它解决不了"三个会话之间的同步由谁做"——那正是人的注意力瓶颈。
- **消息队列 + 工作流引擎**：适合确定性作业与已有服务编排；它不知道 Agent 的步边界、快照与授权语义，外部写仍要自己幂等（03）。
- **直接开 `auto`**：看起来最"自主"。代价是把推断当授权，而原文把提示词注入与凭据泄露列为开放问题；更需要"默认拒绝、可回滚、人可随时接管"的开关，而不是一键放开。
- **全流程人工审批**：最可控，但人又回到每个会话里当调度员；折中是只在高风险动作上要人（07）。
- **把五个模块全搬过来**：最贵，而且公开原型与内部版本并不一致。透镜的价值是找到问题，不是照抄结构。

**结论**：Super-agent 最值得借的不是五个模块的名字，而是那句把瓶颈重新定位的判断——**系统层接管调度与上下文同步，人上移到目标设定与结果验收**。StableAgent 的回答是：先让一次运行可靠、可测、副作用不丢不重，再把多个运行组织成可恢复的协作，最后把动手权关进白名单与审计；每一步都有可证伪的命令。去掉"可靠"，单会话就够；去掉"可审计"，`auto` 也能跑 demo；两样都要，才需要这套看似啰嗦的分层。

## 八、招牌动作：一次演练，把五个设计同时跑出来

运行下面的命令（项目根目录、激活虚拟环境；`--dir` 可换临时目录）：

```bash
python examples/06_superagent_beta.py --phase run --dir .demo-beta
# BETA_RESULT tickets=3 resumed=1 external_comments=1 duplicate_tickets=0 bot_triggers=0

python examples/06_superagent_beta.py --phase report --dir .demo-beta
# BETA_REPORT {... "decisions": {"accept": 4, "observe": 3}, "recovered_assignments": 1,
#              "approvals": {"comment_issue:approved": 1, ...}, "would_accept": 1}

python examples/07_auto_rule_offline.py
# AUTO_DEMO before=observe during=accept after=observe
# AUTO_DEMO ok

pytest -q --no-cov tests/integration/test_superagent_beta.py tests/integration/test_superagent_recovery.py
# 7 passed

pytest -q --no-cov tests/unit/test_supervisor_router.py tests/unit/test_supervisor_runtime.py \
  tests/unit/test_supervisor_views.py tests/unit/test_supervisor_assessor.py \
  tests/unit/test_auto_gate.py tests/unit/test_router_auto.py
# 68 passed
```

逐格断言对应五大设计（**口径**：离线脚本 Worker + 假 GitHub 客户端、注入时钟与 ID、无网络无密钥；macOS + 项目虚拟环境 Python 3.11.15；本次本机单次实测为 `7 passed in 0.83s` 与 `68 passed in 0.54s`，耗时不是结论，断言数字才是）：

| 设计 | 精确断言 |
|---|---|
| 双层 + 事件驱动 | 3 张 Ticket 被创建；`triggers` 中 `issue=3 / issue_comment=1 / ci_status=1` 各留痕；`decisions.accept=4 / observe=3` |
| 两级过滤 | `duplicate_tickets=0`、`bot_triggers=0`；推断候选只记 `would_accept=1`，不建可执行 Ticket |
| 异步 / 人机交接 | 后续评论落 `resume_requires_operator`，人工恢复后同一 Ticket 尝试次数为 `[1, 2]`；对外评论 `external_comments=1` 且经过审批 |
| 存算分离 | 崩溃后 `recovered_assignments=1`；`comment_issue` 效果恰成功 1 次，既不丢也不重放 |
| 外部看门狗 | 只读报告里 `approvals["comment_issue:approved"] == 1`、`notification_counts` 每张票 2 条；报告不含原始 payload |
| 自治档边界 | `before=observe during=accept after=observe`：规则开才接受推断、关了立刻回到只观察 |

两个复现细节：**自动档演示的目录不清理**，重跑前要删掉它建的 `.demo-auto` 数据库，否则事件被去重、决策列表为空，脚本会报错；这与"`--no-cov` 才能单跑测试文件"一样是真实的复现坑。另外，`BETA_REPORT` 是**只读聚合**，不是 Worker 的步边界快照——两者各司其职，别混成一个"状态"。

## 写在最后

Super-agent 给的最有价值的词不是"超级"，而是把瓶颈从"模型够不够强"挪到"人还要管多少会话"。用这面镜子看 StableAgent，会看到一组彼此咬合的选择：Router 与 Worker 分开，入口只产事实、回写不授权限；事件不可变、去重在库、确定性过滤先于模型判断；状态外置、步边界存点、进程可替换而工作不丢；看门功能分散在调用层、编排层、控制层与只读视图里；人只在需要决策与验收时被叫到。

这不是"已经做成了超级智能体"。对外接入口的真实运行、跨月记忆、多实例协作、更聪明的评估器，都还在开放清单上；本文把 StableAgent 已经可证的部分与尚未承诺的部分分开写，就是不想让一张架构图替它们说话。

前面七篇按能力逐块讲透了可靠性、效率、协作与安全；跨篇反复出现的规则——状态完整边界才可存点、默认路径保持安静、状态与副作用同事务、幂等键是命题、版本不明宁可报错、不从文本猜类型、金标准护默认路径、测恢复先于测性能——将在下一篇《设计规范与踩坑手册》连同各自的反例故障收成一张可携带的清单。
