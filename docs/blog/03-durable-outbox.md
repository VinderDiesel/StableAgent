# Durable Outbox：让 Agent 的外部副作用既不丢也不重

> 本文讲解的是一套**与具体项目无关的设计原理**：当一个 Agent 既要改自己的状态、又要对外部世界动手（创建 PR、发通知、启动下游任务），如何让这两件事在崩溃面前既不会"做重"也不会"漏做"。文中代码均为示意，用来把原理讲清楚，而非绑定某一套实现。

前两篇解决的是两个不同层面的问题：checkpoint 解决"我的进程死了怎么接着跑"，context
engineering 解决"这一轮到底发什么给模型"。本篇要解决第三类问题，它既不属于"我"，也不属于
"这一轮"：**你已经对别人做过的事**。

具体一点：Agent 调完模型、跑完工具，接下来要"创建 PR"、"发一条通知"、"启动下一个 Worker"。
这些动作写不进快照——快照能回滚，外部世界不能。于是长期任务 Agent 真正的生产事故往往不是
"模型答错了"，而是"同一件事做了两遍"或者"该做的事没人记得要做"。

> 文中反复出现的「副作用」（side effect）是个计算机术语，借自函数式编程：指一段逻辑除了自身
> 的返回值，还改变了它**之外的**状态。放到这里，就是 Agent 对外部世界（建 PR、发消息、起 Worker）
> 做出的、**一旦发出就无法撤销**的改动——它和 Agent 自己的状态（快照、上下文）不同，后者能回滚，
> 前者不能。后文也用「对外动作」「对世界动手」指代同一件事。

最高效的验证方式是一场地狱演练：让编排进程在"刚发完一半副作用"的瞬间被 `SIGKILL` 打死，重启
后看它能否不多不少地补齐。这类演练的核心断言不是"不超过 N 次"，而是"**恰好** N 次"——写
"不超过"就放走了重复执行，而重复执行在真实仓库里表现为两条 PR、两次评论，不是一个失败的测试。

## 一、为什么状态快照救不了副作用

先排除两个直觉方案，它们都错：

- **先做，再记**：调用外部 API 成功 → 崩溃在落库之前。世界已经被改了，数据库里干干净净，
  恢复时它被重放一遍。
- **先记，再做**：落库成功 → 崩溃在调用之前。数据库说这事做了，世界没变，而且再也没有
  第二次机会——恢复时它跳过这条记录。

错的原因相同：**状态变更和副作用分属两次提交（两次独立的"决定"）**。任何一次崩溃都恰好落在
这两次之间，而那个区间没有任何定义——就像更底层的 checkpoint 里"工具调用发出去了、结果还没
回来"一样，处于一个未被约定的灰色地带。

这揭示了一个更本质的约束：**外部世界没有事务回滚**。你可以回滚自己的数据库，但你没法回滚
"已经发出的那条 Slack 消息"。只要"改自己"和"改世界"不是同一个原子操作，二者之间就永远存在一个
谁都可能先成功、谁都可能先失败的裂缝。

## 二、解法：把"要做的事"变成数据库里的一行

outbox（发件箱）的核心思想，是把"要做的事"也当成数据，和"状态变成什么"**同一次事务**提交。
不再"记下我做了"，而是"记下我将要做"，真正的执行推迟到事务提交之后。示意：

```python
with store.transaction():
    # 1) 改自己的状态
    updated = ticket.update(status=NEXT, queued_at=now)
    store.update_ticket(updated)
    # 2) 把"要对外做的副作用"作为一行写入同一事务
    store.enqueue_effect(
        Effect(
            kind=EffectKind.LAUNCH,
            idempotency_key=f"launch:{assignment_id}:{attempt}",
            payload={"assignment_id": assignment_id},
            due_at=now,
        )
    )
# 事务提交之后，才由独立的执行器去领取并真正调用外部世界
```

于是"记了但没做"变成一种**合法且可恢复的状态**：effect 还躺在表里，`pending`，等着被领取。
真正的执行只在提交之后发生。

- **丢不掉**：因为它已经在磁盘上，和状态变更一起被持久化了。
- **不重复**：因为它带着唯一键，重复入队会被唯一约束挡住。
- **可审计**：任何时刻你都能从表里查到"这个世界动作被请求过没有、被做过没有"。

这一步把原本"两次提交之间的裂缝"压缩成了**一次**提交——裂缝消失了，因为"决定做"和"改变状态"
绑定在了同一个原子操作里。

## 三、幂等键是一个命题，不是一张身份证

光有一张表还不够。崩溃恢复时，同样的逻辑很可能被跑第二遍，于是"这张表自己"也需要幂等。

做法是给每行 effect 加唯一约束：

```sql
UNIQUE (kind, idempotency_key)
```

入队时的语义可以这样定义：

- 命中已 `succeeded | failed | cancelled` 的终态行 → **原样返回，绝不复活**；
- 命中 `pending | retry_wait` → 只更新 `payload` 与 `due_at`，不新增副作用；
- 否则新建。

幂等靠**唯一键 + 数据库约束**，不靠内存里的标志位——内存标志重启即失效，那恰恰是这类系统里
最容易被忽略的陷阱。

关键在于：幂等键表达的是**"这件事（这一次的这次尝试）发生过没有"这个命题**，而不是"某个业务
对象的身份证"。一条 Assignment 可能启动多次，每次尝试应该是**不同的命题**，所以键里要带上
`attempt`；而崩溃恢复时的重启，又必须和原始那次尝试区分开，否则会撞上"终态不复活"规则——新
入队命中那条已经 `succeeded` 的旧行，被安静地领掉，**没有任何报错，但也没有任何 Worker 被重启**。

故障表现是"任务卡住了"，不是"报错了"。这类 bug 不会让任何断言变红，只会让队列静默不动。它比
显式崩溃更危险，因为它通过了所有测试，却在生产里悄悄失效。所以幂等键的形状必须被**数据库约束
和测试同时证明**，而不是靠开发者"记得别写错"。

> 设计要点：把"什么是同一件事"的定义压进数据库唯一键里，而不是压进代码的某个 if 判断里。后者
> 在崩溃恢复、重放、并发这些边界上一定会有人记错。

## 四、事务体内不许 await

上一步能成立，依赖一条很硬的纪律：**事务开启期间，绝不做任何 I/O（尤其是不能 await 一次网络
往返）**。执行器在真正执行副作用前，必须确认自己不在事务里：

```python
async def dispatch_due(self, *, limit: int = 10) -> int:
    assert not store.in_transaction, "handler 的 I/O 不得持有事务"
```

为什么这么刚性？因为在事务内 await 一次外部调用，就意味着**事务的持有时长下限变成了"一次模型
往返"或"一次网络请求"**。在这段不可控的长时间里，你既没提交，也没法判定这个 effect 该不该被
重放——一旦这期间崩溃，你就丢掉了"该不该补做"的判断依据，副作用随之丢失。

这带来一个真实代价：如果存储层是同步的（比如用标准库的同步 SQLite），驱动循环会是单线程、短
暂阻塞的。规模变大后需要换 WAL 模式、独立写线程，或迁移到异步数据库。

但反过来，这条代价也有一个**好的副作用**：同步的存储方法对同循环里的其它协程是**不可分割**的。
所以"状态变更与 effect 入队在同一事务"是可**证明**的，而不是靠团队约定；并发读者只可能看到
提交前或提交后的状态，永远看不到中间态。单线程 + 同步驱动在这里不是妥协，而是把原子性变成
免费的工具。

> 取舍：你要的是"原子性可证明"，为此接受"驱动循环短暂阻塞"。当规模突破这个假设时，再为存储层
> 专门升级，而不是一开始就引入分布式事务去提前支付复杂度。

## 五、内存里没有不可恢复的队列

容易犯的下一个错，是把"现在有哪些任务在跑"记在内存里（一个 `dict[assignment_id, Task]`）。
内存一重启就空了，于是恢复后的进程对"之前在跑什么"一无所知。

正确的做法是：**内存只持有控制句柄（用于取消、用于去重），可运行性的事实源永远是存储层**。每轮
调度都先从存储推导"哪些 Ticket 该跑"，入队 effect；再由执行器领取 due 的 effect，经过门控判断
资格，最后才真正 `create_task` 起跑。

门控函数值得单独读：

```python
def gate_launch(effect) -> bool:
    live = running_assignments()
    if effect.assignment_id in live:
        return False                      # 在途去重
    ticket = store.get_ticket(effect.ticket_id)
    if ticket is not None and ticket.status is QUEUED:
        return False                      # 依赖未满足：停在 QUEUED 不发车
    return len(live) < max_concurrency    # 槽位按活任务数判，驻留不占位
```

门控在"领取"之前发生——不领取，就不消耗重试预算。这把三种"现在不行"分得很清：

| 情形 | 触发点 | 账本 |
|---|---|---|
| 还没到时候（依赖未满足、槽位满） | 门控关闭 | 不进账本：effect 保持 `pending`，`due_at` 不变 |
| 领了才发现不行（等待外部输入） | 抛 `DeferrableError` | 转 `retry_wait`、**退还刚 claim 的那次预算**、固定退避 |
| 真失败 | 抛其它异常 | 吃 `max_attempts` 预算，超限才 `failed` |

这条区分的判据是：**"合法驻留"等多久都不该把 effect 判死**。一个 Worker 暂停等人输入、依赖还没
跑完、槽位被占满，都是"等待"而不是"失败"。如果它们共享同一条重试预算，一个排队排得久的任务会被
**自己的队列位置杀死**——它没做错任何事，却因为等得太久被判定为失败。这是内存队列或粗放重试
策略最容易踩的坑。

## 六、恢复的接缝：从快照恢复，不重放事件

崩溃恢复最微妙的地方在于"如何确定从哪里续"。一个常见错误是：恢复时重放事件流，重新推导状态。
这会引入第二套状态来源，让"恢复语义"变得不可审计——你永远在争论"重放和真实执行是不是一致"。

更稳的做法是：恢复只依赖**存储里已经落定的事实**。例如给每次 Worker 运行注册一个 `run_id`，
崩溃发生在它被注册之前时，恢复就以"同一 Assignment、同一 attempt、但带 `relaunch` 后缀的键"
重新入队，并覆盖注册。恢复路径走的是"读一条既有快照、续跑"，而不是"重放事件、重建状态"。

这条原则背后有一个更重要的判断：**两层系统（比如编排层与执行内核）各自只应有一个崩溃窗口定义**。
编排层复用内核那一个"一步的崩溃窗口"假设，不去发明新的不变式。这样两个模块之间才没有缝隙——
不会互相假装"对方兜住了"。一旦每层都定义自己的窗口，缝隙里就会漏掉那些"谁都没认为是自己责任"
的副作用。

## 七、Event → 副作用结果：只落必要的一条

Worker 内部会吐出大量诊断事件（`Event`）：思考、调用、结果、暂停……但长期领域接口（`Report` /
状态）只需要关心的那几个终态与关键节点。映射应当是**固定且结构化的**：

| 内部事件 | 对外状态 |
|---|---|
| 完成 `DONE` | 就绪，触发下一步 |
| 错误 `ERROR` | 失败，取结构化 reason |
| 暂停-等人 `PAUSED(needs_human)` | 等待人工 |
| 暂停-超预算 `PAUSED(budget)` | 阻塞 |
| 工具结果 `TOOL_RESULT` | 进度（默认唯一开放的进度事件） |

默认只把 `TOOL_RESULT` 这一种映射成"进度"事件，其它高频诊断默认不落库。原因很实际：一旦进度
事件默认高频，长期存储和列表查询的信噪比立刻垮掉，真正重要的状态被淹没。要不要放开到"思考 /
调用"级别，交给配置决定，而不是默认全开。

另一个纪律是：**状态判定只读结构化字段（类型、原因码、错误记录），绝不从消息文本里猜**。文本
是自由的、会变的，用正则去"猜准"一个暂停原因，等于在代码里偷偷建立一条不可靠的保证。如果某条
路径拿不到结构化原因（比如上游只返回终态快照、没有事件流），就**显式降级**为某个兜底状态，并把
这个降级写进文档，而不是在代码里偷偷用文本匹配假装"判断成功"。

还有一处刻意的不收口：任务暂停等待人工时，它在内存里保持运行、占着执行句柄，但槽位随协程返回
而释放——"驻留"由 Ticket 状态表达，不占并发槽位。只有终态事件才正式结束这条 Assignment。

## 八、量级：一轮 tick 是多少

第三节那条文代价（同步存储会阻塞事件循环）到底有多大？在离线、单进程、同步存储的基线规模下
（数十个任务、百来个执行单元、并发上限 50、每轮最多领取 10 条），一轮 `tick()` 的中位数是
**三十多毫秒**，`recover()` 约四十毫秒，把剩余 effect 全部重放到队列静默约一百二十毫秒。

能从这组数字读出的三点：

1. 进程冷热缓存会让首轮偏快，所以以多轮中位数为主，不拿单点 min/max 当结论；
2. 上下浮动十几毫秒属于本机噪声，不应解释成"回归"；
3. 重放耗时主要由"每轮领取上限"决定，而不是由"effect 总数"线性决定——二者要分开测，才能看清
   系统的接缝在哪里。

这组数字的目的，只是验证"在该离线规模下，同步存储不构成瓶颈"，**不构成 SLA、容量规划或跨机器
比较的依据**。规模不同、存储不同、网络尾延迟不同，数字会完全变样——原理不变，量级会变。

## 九、有没有更好的方法

Durable Outbox 是本文的主角，但它不是唯一解。把替代方案摊开，才能说清"为什么是它"：

**1. 事务消息 / 可靠消息队列（Kafka Transactional Producer 等）**
部分消息队列支持"事务性生产"，把发消息和本地事务绑在一起。思路接近 outbox，但前提是**消息队列
本身就是系统的一部分且足够可靠**。如果你的"状态"在数据库、"动作"在 MQ，二者仍然不是同一个事务
源，于是又回到了"两次提交"的老问题——除非 MQ 直接作为状态的系统记录（这通常不现实）。

**2. 变更数据捕获（CDC / Debezium 之类）**
不写 outbox 表，而是直接监听数据库的预写日志（WAL），自动把行变更变成事件流出。
- 优点：应用层零侵入，没有"双写"心智负担，DB 永远是单一事实源；
- 缺点：需要数据库的复制/日志能力，运维复杂；更难把"底层行变更"映射成有业务含义的"领域事件"；
  仍是最终一致，消费端照样要幂等。
当你不想在业务代码里维护 outbox、且有基础设施支撑时，CDC 往往是**比手写 outbox 更优**的选择。

**3. 两阶段提交（2PC / XA）**
让数据库和外部服务参与同一个分布式事务。
- 优点：看起来"完美原子"；
- 缺点：外部服务几乎不支持 XA；事务期间要持有锁直到网络往返结束——这正是第四节点名的"事务时长
  变成一次模型往返"的灾难；可用性在故障时极差。
**基本不适用于"进程 + 外部世界"这种场景。** 它解决的是"两个都支持事务的资源"之间的一致，而
外部副作用（发消息、建 PR）本来就没有事务语义。

**4. Saga / 补偿事务**
把长流程拆成一系列本地事务，每步配一个补偿操作（做错了就反向抵消）。
- 优点：适合跨多个服务的业务编排；
- 缺点：它解决的是"多步流程里某一步失败时如何整体回退"，**并不解决本文关心的单步问题**——
  "我对外部世界这一下到底做没做、做重没做"。而且补偿逻辑本身很难写对（外部动作未必可补偿）。
Saga 是 outbox 的"上游邻居"：你可以先用 outbox 保证单步可靠，再用 Saga 组织多步流程。

**5. At-least-once 投递 + 幂等消费端**
不管内部怎么乱，只管重试发送，赌消费方自己幂等。
- 优点：最简单；
- 缺点：把正确性**完全押在外部系统的善意上**——而现实里你常常控制不了那个 API 是否幂等。
这其实是 outbox 的"下游一半"：outbox 负责**发送端**不丢不重，但消费端幂等仍需单独保证。

**结论**：对"一个进程既要改自己状态、又要对外动手"的常见 Agent 场景，**Durable Outbox 是性价比
的甜点**——它用一次数据库事务消除了最致命的"双写裂缝"，用唯一键保证了发送端幂等，复杂度主要
落在应用层而非基础设施层。当基础设施成熟时，可平滑升级到 CDC；当它演进成跨服务的多步业务流时，
再在 outbox 之上叠 Saga。2PC 在此场景下基本不值得考虑。

## 十、写在最后的检查清单

要给你的 Agent 加"对外界动手"的能力，这八条缺一条就会在生产里出事：

1. 状态变更和它引发的副作用**必须同一次事务**落库。世界回滚不了，只能被准确地记住"已经对它做过什么"；
2. 幂等键是"这件事（这次尝试）发生过没有"的命题，不是业务对象的身份证。恢复路径要么换键、要么
   复用键，选错表现为**静默卡死**而不是报错；
3. 已终态的记录绝不复活；重复入队只允许更新 payload 与 due_at；幂等靠数据库约束证明，不靠内存标志；
4. 事务体内不 await，执行 I/O 前断言无事务——否则一次模型往返的长度决定你的丢副作用窗口；
5. 区分"还没到时候"与"失败了"两套账本，前者**不吃**重试预算；否则排队久的任务会被队列位置杀死；
6. 内存里不留不可恢复的队列，可运行性一律从存储推导，取消句柄和去重句柄不算事实源；
7. 崩溃演练断言"**恰为**"，不断言"不超过"——后者把重复执行放走，而重复执行在生产里是两条 PR；
8. 想给内核开一条新入口时，优先选一个默认 `None` 的可选参数，前提是你有"逐字节一致"的金标准替
   默认路径作证——让"内核是否被动过"这件事只有一个答案。

## 写在最后

本文交出的，是一个**不认识外部世界**的内核：它只管理状态机、durable outbox、单循环调度与崩溃
恢复。它可以启动一个 Worker，也可以在被 `SIGKILL` 之后接着启动——但它启动的 Worker 仍然跑在同
一台机器的同一份代码目录里。

真正把"动手权"关进笼子，还需要受控执行：按任务隔离工作目录、命令边界收成 argv 数组 + 精确白名单、
授权（Mandate）可审计。那是另一篇《受控执行》的主题——它解决的是"即使 outbox 保证只发一次，
发出来的那条命令 itself 是否安全可控"的问题。两者正交：outbox 管"不丢不重"，受控执行管"不该做的
事连发都不该发得出去"。
